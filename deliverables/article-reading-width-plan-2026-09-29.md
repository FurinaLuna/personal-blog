# 文章详情页排版升级计划（加宽正文 + 对齐参考站）

> 交付对象：可直接交给开发（含 AI 开发者）执行的前端改造计划。
> 撰写日期：2026-09-29。触发原因：用户反馈「正文区域好窄」，
> 参考站 `https://xn--ygr25xpohxwz.com/zero-to-fullstack/lessons/module-3-1/`。
> 所有数字都是**无头浏览器实测**，不是估计值；实施时若与本文冲突，先停下来对质本文。

---

## 0. 结论：问题定性

**这不是「调一个 max-width」那么简单，是上一轮目录改造引入的结构性问题。**

我上一轮把右侧目录塞进了 `max-w-content`（700px）的 `<article>` 里，于是：

```
main      1120px   ← 外层 shell（max-w-shell）
article    700px   ← max-w-content
 ├─ prose  444px   ← 正文！被目录挤掉 256px
 └─ aside  224px   ← 目录（w-56）
gap         32px
```

实测（视口 1440×900，无头 Chrome）：

| 指标 | 我们当前 | 参考站 | 差距 |
|---|---|---|---|
| 外层容器 | 1120px | **1407px** | −287 |
| 正文列宽 | **444px** | **873px** | **−429（不到一半）** |
| 正文字号 | 16px | 18px | −2 |
| 行高 | 28px（1.75） | 34.2px（1.9） | — |
| **一行中文字数** | **27 字** | **45 字** | **−18** |
| 目录宽度 | 224px | 272px | −48 |
| 目录 sticky top | 96px | 112px | — |

参考站在 1280 / 1440 / 1920 三个视口下正文都是 **872–880px、45 字/行**，即**固定列宽 + 大留白**，不随视口拉伸。这一点要照抄。

### 一个必须面对的矛盾

仓库 `tailwind.config.js` 里写着：

```js
maxWidth: {
  // 中文正文每行 38~42 字是舒适区，760px 偏宽
  content: '700px',
  shell: '1120px',
}
```

按 16px 字号算，700px ≈ 44 字 —— **这个 token 的注释和数值其实是为「通栏正文」调的**。
但详情页现在是两栏，通栏宽度不再等于正文宽度。所以**不能直接改 `max-w-content`**：
它被 **9 处**共用（`AboutView` / `GuestbookView` / `LinksView` / `NotFoundView` / `UnsubscribeView` /
`App.vue` 崩溃页 / `HomeView` 的窄屏分支 / 详情页的骨架屏与错误态）。

结论：**详情页需要自己的宽度 token，而不是动公共的那个。**

## 1. 范围与硬约束

**范围内**：文章详情页的容器宽度体系、正文列宽、正文字号与行高、目录列宽。
`max-w-content` 的**其余 8 处消费者一行不改**。

**硬约束（逐条验收）**：

1. **不改文章数据结构与渲染管线**：`renderMarkdown()` 的签名、`TocItem` 结构不动（沿用上一轮红线）。
2. **不新增运行时依赖**。字体若要换，只走 `tokens.css` 的 `--font-*` 变量。
3. **颜色/圆角/动效仍只用 `tokens.css` 令牌**，不写死色值。
4. **移动端必须明确降级**：< xl（1280px）无侧栏目录是现状，本计划不得让移动端正文变窄。
5. **目录的 sticky 行为不得回退**：上一轮刚修好「滚长文时目录滚没了」，本轮任何改动后
   必须复跑 `full-check` 的 **E7f**（几何断言，见第 4 节）。
6. **每改一处宽度，都要给出「一行多少个中文字」的实测数字**，不接受「看起来好多了」。

## 2. 目标数值（由实测反推，不是拍脑袋）

### 2.1 正文列宽

参考站是 **873px 列 / 814px 文本块 / 18px 字号 / 45 字**。
本仓库注释认可的舒适区是 **38–42 字**，比参考站略保守。两者取交集：

| 方案 | 列宽 | 字号 | 一行字数 | 评价 |
|---|---|---|---|---|
| 照抄参考站 | 873px | 18px | 45 | 略超本仓库注释口径 |
| **推荐** | **760px** | **18px** | **42** | 落进 38–42 舒适区，与 `max-w-content` 注释口径一致 |
| 保守 | 700px | 18px | 39 | 也合格，但没解决"感觉窄"的观感 |

> 换算依据：中文 1 字宽 ≈ 1em。`760 / 18 ≈ 42.2 字`；`760 / 17 ≈ 44.7 字`。
> 若实施时字体换成衬线（见 2.4），实际字宽会略窄，需**在浏览器里重量一次**再定稿。

**推荐值：正文列 `760px`，字号 `18px`。**

### 2.2 目录列宽

从 224px → **252px**。理由：目录里会出现「模块 3.1：前端基础——HTML」这种长标题，
224px 下会折成两行且很难扫读。参考站是 272px，但它的外层容器也更宽（1407 vs 我们要用的 1280），
252px 是折中。

### 2.3 外层容器

`max-w-shell` 保持 **1120px 不动**（顶栏/页脚共用，改动面太大、收益为零），
详情页用**自己的 `max-w-article` = 1280px**，允许它在宽屏下比顶栏宽。

> 这与参考站一致：它的 navbar 容器 1320px 与正文区同宽；我们的顶栏是 1120px，
> 详情页 1280px 会**比顶栏宽 160px**。这是刻意的（正文优先），但要在视觉上确认不突兀——
> **若觉得突兀，退路是把 `max-w-shell` 一并提到 1280px**（那时顶栏/页脚/首页一起变宽，
> 属于更大的改动，列为决策点 D-排版-3）。

### 2.4 字体（决策点）

参考站用的是**霞鹜文楷 LXGW WenKai → 思源宋体**（楷体感 + 衬线兜底）。
本仓库 `tokens.css` 已经把 `--font-display` 定为 `'Noto Serif SC', 'Source Han Serif SC', 'Songti SC', …`（宋体栈，全本机字体、零加载开销）。

三个选项：

| 编号 | 方案 | 代价 | 观感 |
|---|---|---|---|
| A | **正文保持无衬线**，只加宽字号 | 0 | 现代博客风，与站内其它页一致 |
| B（推荐） | **正文改用 `--font-display`（宋体栈）** | 改 1 行 config | 与参考站接近的"杂志感"；中文宋体在长文阅读上更耐看 |
| C | 引入霞鹜文楷（自托管或外链） | 违反"零字体加载开销" | 最接近参考站，但**本轮不建议** |

> 注意：B 会同时影响**代码块**吗？不会 —— `pre`/`code` 有自己的 `--font-mono`。
> 但会影响行内 `code`？也不会，同上。**需要确认的是**：正文改衬线后，
> `h1/h2` 用的也是 `--font-display`，标题与正文将**同族**，层级靠字重与字号区分——
> 这正是参考站的做法，可接受。

## 3. 实施方案

### 3.1 新增一个语义化宽度 token（`frontend/tailwind.config.js`）

```js
maxWidth: {
  // 通栏正文（关于页 / 留言板 / 友链 / 404 等单列页面）：700px ≈ 16px 字号下 44 字
  content: '700px',
  // 外壳（顶栏 / 页脚 / 首页 / 各列表页）
  shell: '1120px',
  // 文章详情页外壳：比 shell 宽，因为它是两栏（正文 + 目录），
  // 通栏宽度不再等于正文宽度 —— 详情页需要自己的刻度
  article: '1280px',
}
```

### 3.2 详情页容器改造（`frontend/src/views/ArticleDetailView.vue`）

三处 `max-w-content` 的**语义要分开**：

| 位置 | 现在 | 改成 | 理由 |
|---|---|---|---|
| L214 骨架屏 | `max-w-content` | **保持** | 骨架屏模拟正文，跟正文列同宽才对 |
| L223 错误态 | `max-w-content` | **保持** | 同上 |
| L234 `<article>` | `max-w-content` | **`max-w-article`** | 它现在是个两栏容器，不再等于正文 |

然后在正文列上给固定宽度：

```html
<article class="mx-auto max-w-article">
  <header …>            <!-- 标题区：跟正文列同宽，避免标题比正文宽 -->
  <div class="relative">
    <div class="flex gap-14">
      <div class="w-full min-w-0 max-w-[760px] pt-8">
        <MarkdownRenderer :html="rendered.html" />
      </div>
      <aside class="hidden w-56 shrink-0 xl:block">
        <div class="sticky top-24"><TableOfContents :items="rendered.toc" /></div>
      </aside>
    </div>
  </div>
  …
</article>
```

**关键点（逐条都是踩过的坑）**：

1. **`gap-14`（56px）而不是 `gap-8`**：参考站的列间距更大，且 56px 能让「正文列 + 目录列」
   在 1280px 里排开而不挤。
2. **`aside` 必须留在 flex 里、`sticky` 必须在 `aside` 的**子元素**上** —— 这是上一轮
   E7f 修好的结构，**不要回退成「正文 + 绝对定位 aside」**。
3. **`min-w-0` 不能删**：没有它，`flex-1`/`w-full` 子项会被长表格、长代码行顶宽，把目录挤出容器。
4. **标题区（`header`）要与正文列左对齐、同宽**。现在 `header` 直接是 `article` 的子元素，
   会撑到 1280px 满宽；标题比正文宽 500px 会显得散。**建议**给 `header` 也加 `max-w-[760px]`。
5. **点赞区 / 上下篇 / 相关阅读 / 评论区**：它们现在也在 `<article>` 里，会跟着变到 1280px。
   需要逐个决定（见下）。

### 3.3 下半部分各区块的宽度归属

| 区块 | 建议 | 理由 |
|---|---|---|
| 点赞按钮 | 居中即可，无需约束 | 本来就是 `flex justify-center` |
| 上下篇（`sm:grid-cols-2`） | **跟正文列同宽（760px）** | 两张卡片贴在 1280px 两端会离正文很远 |
| 相关阅读（`sm:grid-cols-2`） | 同上 | 同上 |
| 评论区 | **可以放宽到 1280px** | 评论表单有昵称/邮箱/网站三个输入框，宽一点更好用 |
| 系列导航条 | 跟正文列同宽 | 与标题区一致 |

**做法**：给「跟正文同宽」的区块统一套一层 `max-w-[760px]`，而不是给每个区块各写一个宽度。
推荐抽一个小的语义类（见 3.4）。

### 3.4 抽一个类而不是重复写 6 遍（`frontend/src/styles/components.css`）

```css
/* 文章正文的「正文列」：详情页里凡是应该与正文左对齐、同宽的内容（标题区 /
   上下篇 / 相关阅读 / 系列条）都用它，避免在 6 个地方各写一遍 max-w-[760px]
   —— 那样改一次列宽要翻 6 处，迟早漂移。 */
.article-column {
  max-width: 760px;
}
```

> 判断标准符合 `docs/STYLEGUIDE.md`：这套样式会被 3 处以上复用，所以提到 `components.css`；
> 一次性样式仍就地写工具类。

### 3.5 正文字号与行高（`frontend/tailwind.config.js` 的 typography 段）

```js
DEFAULT: {
  css: {
    maxWidth: 'none',
    fontSize: '18px',        // 新增：16 → 18（实测参考站 18）
    lineHeight: '1.85',      // 1.75 → 1.85（参考站 1.9；18px × 1.85 = 33.3px）
    …
  }
}
```

**注意**：`fontSize` 加在 `typography.DEFAULT` 上会**影响所有 `.prose`**——
目前全站只有 `MarkdownRenderer` 用 `.prose`，所以等价于只影响正文。实施时**要确认这一点**
（`grep -rn "prose" frontend/src --include=*.vue`），若将来有第二个消费者，需要改用
`prose-lg` 变体或给 `MarkdownRenderer` 传 class。

### 3.6 目录列宽与字号（`TableOfContents.vue`）

- `w-56`（224px）→ **`w-64`（256px）**，与参考站 272px 更接近、且是 Tailwind 现成档位。
- 层级字号**维持现状**（h2 `text-[13px]` / h3 `text-[13px]` / h4 `text-xs`）。
  > 想更接近参考站可以整体提到 `text-sm`，但那是另一件事（会同时放大移动端抽屉目录），
  > 列为决策点 D-排版-4，默认**不做**。

## 4. 验收标准

### 4.1 几何断言（新增 `full-check` E7g，必须做）

**这条是本计划的硬验收**，因为「感觉窄」这种问题只有量出来才守得住：

```
E7g 正文列宽与行宽：在 1440 视口下
    - 正文列宽 ∈ [740, 900]px
    - 一行中文字数 ∈ [38, 46]
      （用 span 实测单字宽，不硬编码：`prose width / cjkCharWidth`）
    - 目录列存在且 sticky（复用 E7f 的判据）
```

同时**必须复跑 E7f**（目录吸住），确保加宽没把 sticky 弄坏。

### 4.2 响应式降级（必须逐档写下实测值）

| 视口 | 期望 |
|---|---|
| 1920 | 正文 760px（不继续变宽），两侧留白变大 |
| 1440 | 正文 760px |
| 1280（xl 边界） | 正文 760px + 目录 256px = 1072px ≤ 1280 可容纳 |
| 1279（< xl） | 目录隐藏；正文应变为**受 `max-w-content` 约束的窄栏**，不能拉满 1280 |
| 768 | 正文 ≤ 700px，左右留边 |
| 390 | 正文 = 视口 − 左右 padding（现状不变） |

> **1279 那一档最容易出错**：`<article>` 变成 `max-w-article`（1280px）后，
> 在 1000px 视口下正文会拉满 1000px（≈55 字，过宽）。必须给正文列加
> `max-w-[760px]`（已在 3.2 里写了），并在 xl 以下把 `article` 的宽度收回
> `max-w-content`——**推荐写法**：`max-w-content xl:max-w-article`。

**重点回归**：`ArticleDetailView.spec.ts`（37 条）与 `full-check` 的 E5–E8。
宽度改动理论上不影响它们，但 E7a–E7f 依赖目录 DOM，**动了 `aside`/`flex` 结构就要复跑**。

## 8. 风险与不做的事

**风险**：

1. **`fontSize` 加在 typography DEFAULT 会波及全站 `.prose`** —— 实施前必须确认只有一处消费者。
2. **`<article>` 变宽会牵动它里面所有区块**（点赞/上下篇/相关/评论），这是本计划里
   最容易被漏掉的部分；3.3 的表格就是逐块清单，**不要只改正文列就收工**。
3. **xl 断点附近**（1200–1300px）是最容易出问题的一档：目录出现/消失、正文列是否被拉满。
   必须实测 1279 与 1280 两个值。
4. **改宽度会影响截图基线**：`shots/` 里已有旧截图，跑完 `smoke` / `full-check` 会重写，
   这属预期（截图不入库）。

**明确不做**：

- 不动 `max-w-content` 的其余 8 处消费者。
- 不引入霞鹜文楷（违反零字体加载开销）。
- 不重做文章详情页的视觉风格（配色、卡片、圆角）——本轮只解决**宽度与排版尺度**。
- 不动移动端（< xl）的目录入口方案（`MobileToc` 抽屉）。
