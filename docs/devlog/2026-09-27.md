### 为什么这么改

分析报告里，`social_links[].url` 与 `avatar_url` 是**唯一**绕过项目自有规则的
两个用户可控 URL 字段：评论的网站、留言板的网站、友链地址全都走
`app.utils.url.normalize_http_url`，只有这两个没有。而它们渲染在**每一页的页脚**上
（`SiteFooter.vue`），Vue 又不清洗动态 `href`。

`docs/MODULES.md` 明确写着「校验用户可控的 URL 一律用 `utils/url.py::normalize_http_url`
（**唯一实现**）」，所以这是一条被违反的既有约定，而不是新加的限制。

### 踩的坑（本篇最值钱的部分）

**坑 1：校验器加在读模型上，直接把读接口打挂了。**

第一版很自然地给 `SocialLink` 加 `@field_validator("url")`。跑测试立刻红了 8 条，
而且失败信息是 `GET /api/v1/site/profile` 抛 `ValidationError`——`SiteProfileRead`
会 `model_validate` **库里的旧数据**，而种子数据里有一条

```python
{"label": "RSS", "url": "/api/v1/articles", "icon": "rss"}   # 相对路径！
```

相对路径不是绝对地址 ⇒ 校验失败 ⇒ **整个 `/site/profile` 500**。

两个结论：
1. 响应模型没有资格决定「哪些历史数据能读出来」。校验只能放在写入模型上
   （`SocialLinkInput`），这与 `FriendLinkRead` 不带校验器是同一个设计。
   这个坑值得写进注释：它演示了「给共享模型加校验器」的隐蔽副作用。
2. **种子数据自己通不过自己的校验器**——`/api/v1/articles` 是站内相对路径。
   所以规则必须是「拦伪协议」而不是「必须绝对地址」：站内路径对 `href`/`src`
   都安全（浏览器只解析到本站源）。

**坑 2：`//evil.test/x` 看起来像站内路径。**

`urlsplit("//evil.test/x").scheme` 是空串，`startswith("/")` 也为真，所以
「协议为空 + 以 / 开头」这个判据会把它当成站内路径放过去。但它的实际解析结果是
`https://evil.test/x`——**跨域绝对地址**，只是写得更短。所以额外加了
`startswith("//")` 的显式拒绝，并配了用例。

**坑 3（前端测试）：`safeExternalUrl` 在 jsdom 里解析不了相对路径。**

`safeExternalUrl` 内部是 `new URL(candidate)`——**不带 base**。真实浏览器里
`new URL('/api/v1/articles')` 会按 document base 解析成同源绝对地址；但 vitest 的
jsdom 里 Node 的 URL 解析拿不到 document base，直接抛 `Invalid URL`，于是相对路径
被过滤掉、链接不渲染。

我一开始把断言写成「相对路径照常渲染」，结果红了，还顺手用
`Object.defineProperty(window, 'location', ...)` 去固定 origin——**这没用**，
验证过：`window.location.origin` 确实变成了 `https://blog.test`，但
`new URL('/api/v1/articles')` 照旧抛错。最后把这个**已知的环境差异**固化成断言
（「测试环境里被安全过滤」），并在注释里写明真实浏览器行为不同，同时在后端侧
用 `test_site_relative_social_link_is_accepted` 守住「相对路径是合法输入」。

教训：**不要为了让测试变绿去伪造环境**；要把「环境差异」和「产品行为」分开断言，
并写清哪一侧才是真实契约。

| `backend/src/app/db/session.py` | `enable_sqlite_pragmas` 按配置下发 `PRAGMA temp_store` |
| `backend/.env.example` | 文档化 `SQLITE_TEMP_STORE` |
| `.gitignore` | 新增「测试临时区」一节（`.pytest-tmp/` 及两个历史残留目录名） |

### 为什么这么改（以及一个被推翻的判断）

这是**分析报告里那条"本机 5 个测试失败"**的正式收尾。

当时的结论是「SQLite 建不出磁盘临时文件 ⇒ 加 `PRAGMA temp_store=MEMORY`」。
加完确实 735 passed，但**根因判断不完整**：真正让 SQLite 建不出临时文件的是
`tempfile.gettempdir()` 返回了工作目录（`D:\...\personal-blog\backend`），
而那不是 SQLite 的问题，是**测试基础设施**的问题。所以正确做法有两层：

1. **测试层**：测试库 / 上传目录 / pytest basetemp 都不该落在仓库里。
   本机上 `tempfile.gettempdir()` 返回 cwd，于是 `backend/personal_blog_media/`
   与 `pytest-of-<user>/` 都生成在仓库内（`git status` 一直脏着，
   `git add -A` 会把测试媒体提交进去）。现在 `_safe_temp_dir()` 先判
   「可写」再判「不在仓库里」，两条任一不满足就换到 `.pytest-tmp/`（已忽略）。
2. **产品层**：`temp_store` 做成**配置项而不是硬编码**。理由是它有两面性——
   设 `MEMORY` 能绕过「建不出临时文件」的环境（容器里 `/tmp` 只读、
   TEMP 指向不可用路径），代价是临时文件的内存占用改由容器内存上限决定，
   大数据量下可能 OOM。**默认留空**（跟编译期默认走），遇到那种环境再显式打开；
   取值走白名单校验，拼错就拒绝启动（与 `APP_ENV` / `COOKIE_SAMESITE` 同一取舍）。

顺带一提，`_is_writable` 是真的建一个文件再删，不用 `os.access`——
后者在 Windows 上对目录权限的判断不可靠。

## 批次 3：`IntegrityError` 不再一律答成 409

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/main.py` | 新增 `_is_unique_violation(exc)`；`integrity_error_handler` 只在**唯一键冲突**时给 409，其余走兜底 500 信封 |
| `backend/tests/test_integrity_error.py` | 新增 `TestUniqueViolationDiscriminator`：SQLite / PostgreSQL 两方言共 7 条分类用例 + 「拿不到 orig 时不猜」 |

### 为什么这么改

原来 `integrity_error_handler` 把**所有** `IntegrityError` 都答成
409「该内容已存在（可能是同名的分类、标签、用户名、邮箱或链接别名）」。

但 `IntegrityError` 覆盖的不只是唯一键：NOT NULL 违反、外键违反
（例如请求在飞行中作者被删掉，插入带了已失效的 `author_id`）、CHECK 违反
都会落到这里。把它们答成「内容已存在」的后果不是"不够精确"，而是**把排查方向指错**：

- 前端提示用户"换个名字试试"，而问题根本不在名字上；
- 日志与监控看到的是 409（客户端错误）而不是 500（服务端缺陷），
  真正的数据完整性问题就此被掩盖。

判据是方言相关的，两条路都得覆盖（否则会在另一种方言上静默退化成
「一律 500」或「一律 409」）：

- **PostgreSQL**：SQLSTATE `23505`（`unique_violation`）是标准值，优先用；
- **SQLite**：没有结构化错误码，`sqlite3.IntegrityError` 只有一句英文文案，
  只能匹配 `"UNIQUE constraint failed"`。

判据取 `exc.orig`（DBAPI 层原始异常）而不是 `IntegrityError` 本身：
后者的 `str()` 会带上 SQL 语句与参数，里面可能恰好含有 `UNIQUE` 之类的词，
用它做匹配会误判。

### 怎么验证的

```bash

```

另外用一次性脚本直接对 `_is_unique_violation` 跑了 6 个方言组合（SQLite 的

全量后端（ignore 掉需要 `tmp_path` 的备份脚本模块）exit code 0。

## 批次 5：FTS 触发器加 `WHEN` 守卫（并修掉「改了 DDL 对存量库无效」的漂移）

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/db/fulltext.py` | `articles_fts_au` 加 `WHEN` 守卫；新增 `_refresh_update_trigger` 自愈逻辑；`_normalize_sql` 剥掉 `IF NOT EXISTS` |
| `backend/alembic/versions/20260927_2210_f3b7c1a95d24_guard_articles_fts_trigger.py` | 新迁移：`DROP` + `CREATE` 重建该触发器（幂等），downgrade 还原旧定义 |
| `backend/tests/test_fts_trigger_guard.py` | 新增：守卫语义 3 条 + 定义漂移 2 条 + 自愈 2 条 |

### 为什么这么改

`articles_fts_au` 原来没有 `WHEN` 守卫，于是 `articles` 上**任何** UPDATE 都会触发
「delete + insert」一对 FTS 写操作。而详情页每次访问都会 `view_count + 1`
（点赞同理）——**读一次文章就重新分词一次整篇正文**，实测 100KB 正文 4.73ms、
30KB 1.42ms，与正文长度线性相关。

### 踩的坑（这一节比改动本身值钱）

**坑 1：`CREATE TRIGGER IF NOT EXISTS` 不会更新已存在的触发器。**

三条触发器都是这么建的，所以只改代码里的 DDL 对**存量库完全无效**：新库拿到新定义、
老库留着旧定义，而且没有任何报错。这类 "改了却对存量库不生效" 的 DDL 漂移只能靠
迁移修，因此额外加了迁移；同时在启动钩子里加了「定义漂移就重建」的自愈，
覆盖"自动建表不跑迁移"的开发路径。两条路径都有测试。

**坑 2：SQLite 存 DDL 时会把 `IF NOT EXISTS` 去掉。**

自愈的比较逻辑一开始恒定判为"不一致" ⇒ **每次启动都 DROP + CREATE 一次触发器**。
是「定义漂移」那条测试先红的，排查时把库里的 `sqlite_master.sql` 打出来才看见
（常量里是 `CREATE TRIGGER IF NOT EXISTS x`，读回来是 `CREATE TRIGGER x`）。
所以在 `_normalize_sql` 里显式剥掉这个短语——**比较 DDL 时不能假设两边字面相同**。

**坑 3：守卫必须用 `coalesce(...) IS NOT coalesce(...)`，不能写 `new.x IS NOT old.x`。**

`summary` 是**可空列**。一旦旧值是 NULL，`IS NOT` 得到 NULL，整个 AND 短路，
触发器就不跑了 —— 而「把 summary 从 NULL 改成有值」正是必须重建索引的情况。
这类错误不会报错、只会"某些更新没生效"。专门写了一条
`test_summary_null_to_value_reindexes` 守住它。

**坑 4（测试环境）：trigram 分词器要求查询词 ≥3 字符。**

## 批次 6：refresh 复用窗口不再滑动 + `/auth/refresh` 限流

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/models/refresh_session.py` | 新增不可变的 `first_rotated_at` 列 |
| `backend/src/app/repositories/refresh_session_repository.py` | `mark_rotated` 只在第一次写入 `first_rotated_at` |
| `backend/src/app/services/auth_service.py` | 复用判定的锚点改为 `first_rotated_at` |
| `backend/src/app/api/v1/auth.py` | `/auth/refresh` 补 `rate_limit("refresh", 30, 60)` |
| `backend/alembic/versions/20260927_2235_a4c9e2f71b38_add_refresh_session_first_rotated.py` | 新迁移加列（可空，旧行回退到 `rotated_at`） |
| `backend/tests/test_refresh_rotation.py` | 新增滑动窗口回归用例；`_set_rotated_at` 同步改两个字段 |
| `backend/tests/test_ratelimit.py` | 新增刷新限流 2 条 |

### 为什么这么改（漏洞本身）

`AuthService.refresh` 用 30 秒的宽容窗口容忍「两个标签页同时刷新」，
而这个窗口原本按 `rotated_at` 计算——偏偏 `mark_rotated` **每次调用都会把它重置成
"现在"**（原有的 `replay(client, first)` 走的正是这条路径）。于是窗口会滑动：

    攻击者持有一枚已用过的 refresh token，每 <30 秒重放一次：
    每次都落在窗口内 ⇒ 放行 ⇒ mark_rotated 把 rotated_at 推到当前
    ⇒ 下一次重放又落在窗口内……无限续期，而"复用即吊销整个会话族"永不触发。

`first_rotated_at` 只在第一次轮换时写入、之后不再更新，用它算窗口就滑不动了。
旧行该列为 NULL，服务层用 `record.first_rotated_at or record.rotated_at` 回退，
所以升级不会误判历史数据。

### 这一节的重点：我写了两版**测不出漏洞**的回归用例

第一版："容忍一次重放 → 睡过窗口 → 再重放一次，断言 401"。
**在有漏洞的实现上它照样通过**——因为第二次重放的年龄是按 `rotated_at`
（上一次重放时刻）算的，睡 1.2 秒同样超窗。**单次重放不构成攻击**。

第二版改成"卡着窗口持续重放"才算对：窗口 monkeypatch 成 0.15 秒、
重放间隔 0.08 秒（**小于窗口**）、连续 4 次。这时两种实现才分岔：

| 实现 | 每次重放看到的年龄 | 结果 |
|---|---|---|
| 有漏洞（锚点 = `rotated_at`） | 恒为 ~0.1 秒 < 0.15 | 一路 200，**永不吊销** |
| 修好（锚点 = `first_rotated_at`） | 从第一次轮换累计，很快 > 0.15 | 出现 401 并吊销整族 |

**间隔必须小于窗口**，否则"最近一次使用"的年龄也超窗，两种实现都会拒绝，
用例同样失去判别力（这是我第二版又踩的坑）。

验证方式是把实现临时改回有漏洞的版本再跑：

```
anchor = record.rotated_at          → FAILED（状态码全 200，一次 401 都没有）
anchor = record.first_rotated_at...  → 1 passed
```

日志里能直接看到漏洞的形状：`anchor` 每次都往后跳 ~0.1 秒，
而 `first_rotated_at` 始终钉在第一次轮换的时刻。

**教训**：安全类回归用例必须验证"它在有漏洞的实现上会红"。
前两版都通过了 `pytest`，却什么都没守住——比没有用例更危险，因为它给了虚假的信心。
另外还犯了个操作错误：临时改实现时用 PowerShell 正则替换，模式里误带了一段
`PS C:\>` 提示符，替换从未生效，于是"有漏洞的版本也能通过"这个假象多花了一轮排查。
**改完要回读文件确认替换真的落上了**（`Select-String` 打出来看一眼）。

## 批次 8：`article_tags` 补反向索引（并把"索引真的被用上"变成断言）

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/models/associations.py` | `article_tags` 声明 `Index("ix_article_tags_tag_id", "tag_id", "article_id")` |
| `backend/alembic/versions/20260928_1250_b8e4d1c7a920_...py` | 新迁移，幂等补建（先查 `has_table` 与 `get_indexes`） |
| `backend/tests/test_indexes.py` | 新增：索引存在性 + **查询计划证明它被用上** |

### 为什么这么改

`article_tags` 原先只有主键 `(article_id, tag_id)`，那个复合索引只服务
「这篇文章有哪些标签」这个方向；而项目里两个高频查询要的是**反方向**
`tag_id -> article_id`：

1. 按标签筛文章 —— `Article.tags.any(Tag.slug == ...)`；
2. 标签云计数 —— `article_tags JOIN tags ON tag_id = tags.id`。

SQLite 与 PostgreSQL 都**不会**自动为复合主键建反向索引，于是这两条只能对
`articles` 做全表扫描 + 逐行 `EXISTS` 判定，随文章数线性变慢。索引的第二列
`article_id` 是刻意加的：让连接变成 covering，不必回表。

### 方法论：区分"建了索引"与"索引被用上"

功能测试对这两者的反应完全一样——**都是绿的**，只是后者慢。所以
`tests/test_indexes.py` 用 `EXPLAIN QUERY PLAN` 断言计划里出现该索引，
并反向断言不出现 `SCAN at`（索引缺失时正是那个形状）。实测对比：

```
升级后：SEARCH at USING COVERING INDEX ix_article_tags_tag_id (tag_id=?)
降级后：SCAN at          ← 退化形状，正是这条断言要拦住的
```

迁移实跑了 upgrade → downgrade → upgrade 三轮，每轮读 `PRAGMA index_list`
与查询计划核对。

### 同类但**本轮没做**的项（诚实记录）

- **归档 N+1**：`archive_groups` 逐月查询是**代码里注明的有意选择**
  （月份数是个位数，每月有 limit 保护）。真正的成本在谓词形状
  （`substr(cast(时间, 文本), 1, 7)` 让索引失效），改它要引入 `published_ym`

  留作后续。
- **列表投影**：列表查询仍 `select(Article)` 取整行（含 `content_md`）再由

- **前端 hljs 懒加载**（ROADMAP 3.2，可省 ~49.5KB gzip）：它要重构

重的那半放 `codeHighlightEngine.ts`，**只经由 `import('./codeHighlightEngine')` 到达**。

hljs 核心在这个闭包里吗？ False

## 批次 11：归档按月谓词去掉「列的函数」——materialised `published_ym`

对应分析报告 **H2（归档接口 N+1 次全表扫描）**。批次 8 的日志里把这一项记为
「留作后续」，理由是"收益对几十篇文章的站点不明显"——这次动手后要修正那句话：
真正贵的不是查询次数，而是**每次查询都从表头扫到尾**，而端点是公开、无缓存、无限流的。

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/models/article.py` | 新增 `published_ym`（`String(7)`）+ 索引 `ix_articles_status_published_ym(status, published_ym)`；新增 `derive_published_ym()` 与 `before_insert` / `before_update` 两个事件 |
| `backend/alembic/versions/20260928_1500_c3d7a1f4e8b2_add_articles_published_ym.py` | **新增**：加列 → 回填 → 建索引；`downgrade` 反向（先删索引再删列） |
| `backend/src/app/repositories/article_query_repository.py` | `list_archive` / `list_by_month` 改成裸列比较；抽出 `_archive_stmt` / `_by_month_stmt`（查询计划断言要能拿到同一条语句） |
| `backend/src/app/services/article_query_service.py` | `archive_groups` 的 docstring：N+1 仍是有意选择，但**前提**改成"每次查询走索引" |
| `backend/tests/test_indexes.py` | `TestPublishedYmArchiveIndex`：列/索引存在性 + 3 条查询计划断言（含一条反向验证） |
| `backend/tests/test_articles.py` | 归档 4 条（月份来源 / 草稿发布 / 定时发布 / 改期）+ 派生列本身 2 条 |
| `backend/tests/test_seed.py` | 演示数据（第三条写路径）也带上归档键 |

### 为什么这么改

旧谓词是

```sql
substr(cast(coalesce(published_at, created_at) as text), 1, 7) == '2026-09'
```

**列的函数**，任何索引都服务不了它；而且表达式里含 `created_at`，索引里没有这一列，
所以还必须回表取整行。3 年博客（36 个月）= 1 + 36 次全表扫描。

N+1 结构**没有动**，这是刻意的：`archive_groups` 的 docstring 里写明「月份总数通常
个位数到十几，每月有 limit 保护」。要修的是**每次查询的代价**，不是次数——
谓词可索引之后，N 次查询各自变成一次索引 seek；改成一次 JOIN + 窗口函数取每月前 N
仍然要对整表做函数计算，复杂度上去了，收益却只是"省掉几次 seek"。

### 四个关键决策

**1. 为什么是 materialised 列，而不是表达式索引 / 生成列。**
PG 的表达式索引只在 PG 上有；SQLite 的生成列（`GENERATED ALWAYS AS ... STORED`）
**不能通过 `ALTER TABLE ADD COLUMN` 加**（SQLite 只允许加 VIRTUAL 生成列），
而"改了却对存量库不生效"正是批次 5 花了一整轮修的坑。普通列 + 迁移回填 + 写路径维护
两条方言语义完全一致。

**2. 维护逻辑放在模型事件（`before_insert` / `before_update`），不放服务层。**
写入点分散在两层：`ArticleCommandService.create/update`（新建、改标题、改发布时间、
发布草稿、定时发布）与 `services/seed.py` 的演示数据。服务层维护意味着每加一个写入口
都要记得补一行，**漏了不会报错**——只会让文章从归档页上静静消失。
模型事件一次覆盖所有 ORM 写路径，于是那两个文件（不在本次写范围内）**零改动**就正确。

**3. `before_insert` 里必须显式把 `created_at` 落定。**
SQLAlchemy 派发 `before_insert` 的时刻**早于**列默认值求值
（`orm/persistence.py`：`_organize_states_for_save` 先派发事件，之后才
`_collect_insert_commands`），所以此刻 `target.created_at` 还是 `None`。
草稿（`published_at` 为空）的月份只能来自 `created_at`——不落定就只能写 NULL，
而迁移回填会给存量草稿填上月份，于是**老行有值、新行没有**。
现在两列由同一次 `datetime.now(UTC)` 算出，也顺带消掉了"跨月零点插入时两列差一个月"
这种一年撞一次、撞上也无从发现的可能。

**4. `before_update` 只在 `published_at` / `created_at` 真的变了时才重算。**
月份与 `status` 无关（旧谓词同样不看状态），所以状态变更、改标题都不该重算；
浏览/点赞自增走 Core `update()`，根本不经过 mapper 事件。判断条件与列的定义域严格对齐，
"跳过"永远是安全的。

顺带：回填写成 SQL 里的 `COALESCE(published_at, created_at)` 字面量，**刻意不 import
应用代码**——迁移要能在任意历史版本的代码上重放（沿用批次 5 立下的约定）。

### 踩的坑（本篇最值钱的一条）

**坑 1：我原本以为"旧谓词一定全表扫描"，实测不是 —— 也因此差点写出一条没有判别力的断言。**

建好索引后，把谓词换回旧的 `substr(...)` 形式再 `EXPLAIN QUERY PLAN`：

```
新写法：SEARCH articles USING INDEX ix_articles_status_published_ym (status=? AND published_ym=?)
旧写法：SEARCH articles USING INDEX ix_articles_status_published_ym (status=?)
```

索引**照样出现在旧写法的计划里**——因为复合索引的前导列 `status` 被
`status IN ('published')` 用上了。区别在**月份那一维没有约束**：旧写法每个月份都要
从索引里读出全部已发布行、再回表逐行算 `substr`。

所以"断言计划里出现索引名"是个**几乎恒真的断言**（旧代码也能通过）。
`tests/test_indexes.py` 的判据因此改成 `published_ym=?` 必须出现在计划里，
并额外加了一条**反向用例**：旧谓词的计划里必须**没有** `published_ym=?`。
——这正是批次 6 那条教训的同类：**写完回归用例要问"它在修改前会红吗"**，
只不过这次判别力问题出在"断言太弱"而不是"场景选错"。

**坑 2：`pytest` 的 `-q` 和 `pyproject` 的 `addopts = "-q"` 叠加成 `-qq`，就不再打印
`N passed` 那一行。** 第一次跑完只看到 exit code 0、没有任何数字，一度以为命令没跑起来。
拿到数字要走不带额外 `-q` 的那次运行（或看 exit code + `--co` 计数）。
`-qq` 下终端只剩进度点，非常适合脚本，但**不适合需要报数字的验收**。

**坑 3：SQLite 的 `DROP COLUMN` 不允许该列上还挂着索引**（报错方向很明确，但顺序写反
就是一条失败的 `downgrade`）。所以 `downgrade` 必须先 `drop_index` 再 `drop_column`。
