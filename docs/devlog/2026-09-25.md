## 一、凭证迁移：refresh token → httpOnly Cookie（P0-1）

提交：`9c66052`（前端）、`36e19cf`（后端）、`94ccef7`（刷新接口 body 可选）、
`bf37c6b`（E2E 脚本）、`e9b2007`（e2e_live）

### 为什么做

access + refresh 双令牌都明文躺在 `localStorage`。`refresh_token` 是**能自我续期**的
长效凭证（7 天）：一次 XSS 就能把它读走，并在轮换链上反复换出新的 `access_token`，
服务端既看不见也拦不住。Markdown 用 DOMPurify 消毒显著压缩了 XSS 面，但**消毒是降低
概率，不是消除风险**。

### 落地形态

| | 存放位置 | 属性 |
|---|---|---|
| `access_token` | 前端内存（模块级变量） | 120 分钟；刷新页面即丢失 |
| `refresh_token` | httpOnly Cookie | `Path=/api/v1/auth`、`SameSite=Lax`、生产加 `Secure`；7 天 |

响应体默认**不再**返回 `refresh_token`（只有 `REFRESH_TOKEN_IN_BODY=true` 才带一份，
给 curl / CI 这类拿不到 Cookie Jar 的客户端）。

### 放弃的方案，以及为什么

- **CSRF Token**：Cookie 会被浏览器自动附带，所以确实需要一道 CSRF 防线。但我们用
  **`Origin` 白名单**而不是签发 Token。理由：本站只有一个前端、同源部署是默认形态，
  而 CSRF Token 需要额外的签发 / 存储 / 轮换 / 跨标签页同步，成本明显更高。将来若真出现
  "第三方站点要调这些接口"的需求，那时再补 Token 也不迟，两层可以共存。
- **`SameSite=Strict`**（审计报告里建议的是 Strict）：会连"从外部链接点进来"都带不上
  Cookie，用户体验上表现为"点开文章链接后顶栏显示未登录"。取 `Lax` 作为默认，
  跨站场景由 `Origin` 白名单兜底。
- **短期缓解项（refresh 绑定 UA + IP 段指纹 / 后台会话单独缩短有效期）**：审计给的
  (a)(b) 两条都没做 —— 既然做了根治方案，指纹绑定只会引入"换网络就掉线"的新问题。

### 代价（必须记住，不是可选项）

1. **刷新页面必须靠 Cookie 静默续期**。access token 不落盘，所以每次页面加载都要先换
   一枚新的再问 `/auth/me`。这条路径断了就是"刷新任意页面即被登出" —— 前后端各有用例守着。
2. **`CORS_ORIGINS` 从此兼作安全白名单**，不只是 CORS 配置。分域部署时前端来源必须写进去，
   否则刷新一律 403，而症状不是"某个接口挂了"，是"登录用户刷新任意页面即被登出"。
3. **`SameSite=Lax` 会拦掉跨站 XHR**：前后端不同域必须设 `COOKIE_SAMESITE=none`，
   而 `none` 强制要 `Secure`，否则浏览器直接丢弃该 Cookie。生产门禁会拒绝这个组合。

### 关键实现决定

- **Cookie 的签发 / 读取 / 清除 / 同源校验集中在 `api/cookies.py` 一个文件**。原先
  "三处各写一份 set_cookie"迟早漂移，而漂移的表现是"登出后还能刷新"这种安全洞。
- **取 token 的优先级是「显式 body > Cookie」**。这不只是兼容，而是让"拿 access token 去
  刷新应当被拒"这类反向用例仍然成立 —— 否则浏览器存在 Cookie 时会把本该失败的请求悄悄
  救回来，测试就失去意义了。
- **续期的单飞锁必须同时覆盖"启动静默续期"与"401 触发续期"两条路径**。它们是两个入口，
  若各发一次 refresh，后端的滚动轮换会让其中一个失败 —— 用户表现为"刚打开页面就被登出"。
- **路由守卫去掉了 `tokenStore.access` 判断**。改造后刷新页面时内存里一定没有 access token，
  留着这个条件会把有登录态的用户判成未登录并弹去登录页。

### 踩坑（本节最值钱）

**1. 我把一个测试环境的产物误判成了真缺陷，并据此改错了安全代码。**

现象：E2E 里 `POST /auth/refresh` 返回 403，导致整页刷新后被弹回登录页。我判定是
"Vite 代理改写 `Origin` 导致白名单失配"，于是改 `cookies.py`：加了「本机端口互换」
的白名单扩展，还一度改成「拿 `Origin` 比对请求自身的 Host」。

两个错误：

- 那个 403 是我**自己用非白名单端口（5175 / 5176 / 4173）搭临时栈**造成的；
  `backend/.env` 的 `CORS_ORIGINS` 只列了 `localhost:5173,127.0.0.1:5173`，
  它会**覆盖** `config.py` 里的默认值（默认含 4173），所以任何非 5173 的端口都会 403。
- 改成"比对 Origin 与请求自身 Host"是往坏处改：那等于"我声称什么 Host 就认什么"，
  削弱了防线（攻击者只要同时伪造 `Host` 和 `Origin` 就能过）。

已 `git checkout` 撤销。原始的白名单实现本来就是对的（实测 `Origin: http://localhost:5173`
→ 401 放行、`http://evil.example.com` → 403 拦截）。

**教训**：改安全代码前，先确认症状能在**标准配置**下复现。在自建环境上归因，会得到一个
听起来合理、实际错误的结论，而且改出来的代码比原代码更差。

**2. `--reload` 不可靠，会让人在旧代码上做判断。**

我两次拿到 403，探测的后端进程跑的都是**旧代码**（没有 Cookie 支持）。判定手法：
curl 一次，看响应体里有没有新字段。改完后端代码、跑 E2E 之前，先确认进程真的加载了新代码。

**3. Vite 的 `changeOrigin: true` 只改 `Host`，不改 `Origin`。**

实测：经代理后后端看到 `host=127.0.0.1:8001` 但 `origin=http://127.0.0.1:5175`。
生产 nginx 用 `proxy_set_header Host $host`，保留原始 Host。两边行为不同，别把开发现象
当作生产现象。

**4. `full-check` 通过 ≠ 覆盖了 `e2e_live`。这是我被 CI 抓到的盲区。**

CI run #55 红在 `tools/e2e_live/e2e_run.py:748` —— 它从登录响应体读 `refresh_token`，
现在那里是 `None`。A01 一挂，`STATE["admin_token"]` 未赋值，下游 15 条用例连锁
`KeyError`。我上一批只把改动派给了 `tools/*.mjs`（浏览器脚本），漏了这个 Python 脚本，
本地也没跑。

**教训**：`tools/` 不是 `tools/*.mjs`。这两个脚本跑的是完全不同的层 —— 浏览器 UI
vs 真实 HTTP + 直连数据库复核。改了认证契约，两个都要跑。

**5. 迁移后出现了一批"永真断言"。**

E2E 里原来的登出断言「`localStorage` 里两个 key 没了」在迁移后**恒为真**（新代码根本
不写它们）；「页面内裸 `fetch /auth/me` 返回 401」也恒为真（access token 只活在 axios
拦截器里，裸 fetch 从来带不上）。已改成两个真实证据：重新访问受保护后台页被路由守卫
弹回 `/login`，以及 CDP 确认服务端的删 Cookie 指令生效。

同类问题：`test_refresh_without_a_body_still_works` 实际发的是 `json={}` —— 用例名与
实现不符，发空对象根本守不住「body 可省略」这条契约，改了签名也不会让它变红。

## 二、生产门禁加固（P0-2）

提交：`b68d3d0`、`aa1202c`

- **迁移入口此前完全不过门禁**。`check_production_safety()` 只在 `create_app()` 里调用，
  于是 Alembic、`backup_db.py`、`e2e_run.py` 都绕过去了 —— 而 Alembic 恰恰是拿着生产库
  权限、最容易"配置还没配好就先跑迁移"的进程。症状是"库建好了但服务起不来"。
  现在 `alembic/env.py` 复用同一个函数，规则不会两边漂移。
- 门禁新增三条：`CORS_ORIGINS` 为空或含 `*`（CORS 中间件开着 `allow_credentials=True`，
  通配等于把凭证发给任意站点）、`DATABASE_URL` 指向 SQLite 上生产、
  `COOKIE_SAMESITE=none` 但未启用 `Secure`。
- **`--workers 1` 不变式写进测试**：`test_deploy_config.py` 从 Dockerfile 的 exec 形式
  CMD 按 JSON 解析 token，断言 `--workers` 紧邻值就是 `"1"`，并断言 compose 里没有
  `WEB_CONCURRENCY`（uvicorn 会读它，能覆盖 CMD 让断言失效）。

**修门禁时踩的坑**：`SAFE_PRODUCTION` 测试夹具原先没写 `database_url`，而字段默认值就是
SQLite —— 加上"SQLite 上生产"这条校验后，这份"安全配置"夹具自己反而不安全了。
改门禁时要想清楚：哪些看起来安全的夹具其实不安全。

## 三、部署配置（`aa1202c`）

- **空串被当成真值**：pydantic-settings 没开 `env_ignore_empty`，所以 `COOKIE_SECURE=`
  （保留键留空）会让 bool 解析失败、应用起不来；`COOKIE_DOMAIN=` 会写出 `Domain=` 为空的
  Cookie，浏览器不认。而 compose 用 `${COOKIE_SECURE:-}` 透传时**必然**产生空串。
  现在空串统一按"没配"处理，显式值仍原样生效。
- **compose 没透传 `COOKIE_*`**：默认拓扑（nginx 同源反代）用不到，但分域部署必须能改。
  不显式列出，运维就没法在根 `.env` 里配 —— 这与仓库既有约定一致
  （根 `.env.example` 的"没写等于不存在"，`test_deploy_config.py` 守着它）。

## 四、检索可观测性（`9f861d4`）

`_ensure_fulltext_index()` 原先挂在 `db_auto_create` 分支里，而生产
`DB_AUTO_CREATE=false` —— 等于**生产上根本不探测索引**，PG 下 `pg_trgm` / GIN 索引缺失时
搜索会静默退化成三列 LIKE 全表扫且无人知晓。现在无条件探测，并把 `search_index` /
`search_accelerated` / `search_detail` 拼进 `/ready`。

**刻意不把索引缺失算进就绪判定**：性能退化不是服务不可用，算进去会让一次索引问题触发
整站摘流，放大成可用性事故。

顺带删掉前端零消费的死配置 `VITE_SITE_TITLE`。

## 五、多 worker 的运行期自检（`b37533c`）

限流是**进程内**固定窗口计数（`utils/ratelimit.py`，计数在内存 dict 里）。多开 worker
的后果不是"性能变好"，而是配额按 worker 数线性放大 —— 登录 5/分 在 4 worker 下变成
20/分，爆破成本降到四分之一，**日志里一句告警都没有**。

此前只有 `tests/test_deploy_config.py` 静态断言 Dockerfile / compose 写了 `--workers 1`，
挡不住"有人裸机用 `uvicorn --workers 4` 起"。现在启动期检查 `WEB_CONCURRENCY` /
`UVICORN_WORKERS` 与 `sys.argv`（覆盖 `--workers N` / `-w N` / `--workers=N` 三种写法），
**生产 RuntimeError 拒绝启动、非生产只记 warning**（与既有生产门禁同一取舍：
开发时临时多开 worker 不该起不来）。空串按"没配"处理，与 `COOKIE_SECURE` 同一约定。

**关键取舍：把局限写进 docstring，而不是假装完备。** 它只能看到 `sys.argv` 与环境变量，
因此**覆盖不了编程式启动**（`uvicorn.run(app, workers=4)` 的 argv 里可能没有 `--workers`）。
刻意不去数子进程或读 `/proc`：那类做法在"Windows 开发机 + Linux 容器"的跨平台约束下
不可靠，还会引入一堆自己的边界情况。它是一道**拦最常见误用的门槛，不是不变式**。

**测试上的一个小坑**：非生产告警` 用 `caplog` 捕获不到 —— `setup_logging` 把 blog logger 的
`propagate` 设成了 `False`，而 `caplog` 挂在 root 上。改用直接替换 `main.logger.warning`。
这点写进了注释，免得下一个人重新踩。

## 六、会话提示 Cookie：消掉匿名访客每次进站多余的 401（`1b847ad`）

### 问题

access token 只存内存后，前端**无法从 JS 侧判断**这台浏览器有没有会话，于是连公开页面
也会先打一次 `POST /api/v1/auth/refresh` —— 匿名访客每次进站白吃一个 401。
这是凭证迁移引入的代价（见第一节"代价"），本次消掉它。

### 方案与一个我自己写错的地方

方案是再下发一个**非 httpOnly** 的「提示」Cookie（`blog_session`，值恒为 `"1"`），
前端读它决定"值不值得去续期"。

**我最初给的规格是错的**：要求它"属性与 refresh Cookie 对齐（含 `path=/api/v1/auth`）"，
同时又说"JS 要能读到"—— 这两条互相矛盾。Cookie 的可见性受 path 约束，`/api/v1/auth`
作用域的 Cookie 在 `/` 页面上 `document.cookie` 读不到，hint 会**永远为 false**：
不只是优化失效，还会连带**丢掉公开页的登录态恢复**（已登录用户打开首页，顶栏显示"访客"）。

更麻烦的是这个 bug 会被测试掩盖：用例里写不带 path 的 `document.cookie = 'blog_session=1'`
时 jsdom 默认路径就是 `/`，读得到，测试全绿，线上却是坏的。

执行的同学在动手前停下来指出了这一点（**这是本批里最有价值的一次拦截**），
最终定为 `path=/`，并把这条坑钉成**双向用例**：正向用生产真实 path 断言读得到；
反向显式断言 `path=/api/v1/auth` 的提示 Cookie 在 `/` 页面读不到 —— 后者是用例化的护栏，
以后谁"为了对齐"改回去会立刻变红并指向原因。

### 边界（都写进了代码注释）

1. **`path` 是唯一的隐形地雷**：必须 `/`，与 refresh Cookie 刻意不同。
2. **跨域部署（未设 `COOKIE_DOMAIN`）时 SPA 读不到它** → 退化成"公开页不恢复登录态"
   （受保护页仍正确，不会锁死用户）。跨子域请设 `COOKIE_DOMAIN`；完全不同的域之间
   无法共享 Cookie，这个优化在该形态下天然不可用。
3. **提示与实际会话可能不一致**：所以受保护路由**坚决不拿它当判据**（原样保留无条件恢复）。
   这里最怕后人图快把 hint 也用到受保护分支 —— 那会立刻变成"偶发被登出"。
4. **没有引入新的安全面**：值恒为 `"1"`、非 httpOnly 是刻意、服务端不认它，
   XSS 读它无额外收益。代价只是它会跟着 `/media` 等请求一起发出去，无信息价值。
5. **一个更简单但被否决的替代**：前端在登录成功时自己写一个 `localStorage` 标记。
   省掉一次 Cookie 往返，但它不会随 refresh token 过期自然失效，且登出要靠 JS 保证
   清干净 —— 比 Cookie 更容易漂移。

### 一处连带修正

`tests/test_refresh_cookie.py::test_cookie_is_not_sent_to_unrelated_paths` 原先断言
业务接口 `GET /api/v1/articles` 的请求**没有 Cookie 头**。hint 用 `path=/` 后这个头必然出现。
没有绕开它，而是把断言改成精确表达原意：**业务接口上不得出现 refresh token 的值**，
并显式断言 hint 确实会带上（记录这个刻意的例外）。
