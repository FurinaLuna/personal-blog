### 坑 3：`full-check` 的 A5c 四条连锁失败 —— 友链 URL 写死撞唯一约束

A5c-1 报 `id=undefined`、A5c-2 报「公开列表 3 条」，**四条全红且失败信息完全不提原因**。
用纯 HTTP 复刻「创建 → 立刻读」，拿到真正的响应：

```
POST /links: HTTP 409
{"detail":"友链地址「https://example.com/e2e-link」已被收录","code":"conflict"}
```

A5c 用的是 `E2E 友链 ${RUN}`（名字带 run id）但 **URL 写死**，而友链地址上有唯一约束。
上一次 full-check 异常中断留下的那条记录占着这个地址 → 本次创建一律 409 →
按名字查不到 → 后面隐藏/删除三条全部连锁失败。

修法：`linkUrl = \`https://example.com/e2e-link-${RUN}\``，并清掉那条孤儿记录。
修完 **64/64**（当时是 63 条；批次 2 加的 E7f 让它变成 64 条），cleanup 里也出现了 `friend-link#4:200`。

> 教训：**E2E 造数据时，凡是带唯一约束的字段都必须带上 run id**。
> 只让「名字」唯一是不够的 —— 约束可能落在别的字段上（这里就是 URL）。
> 另外，失败信息应该直接带上接口原始响应，否则 `id=undefined` 会把排查方向彻底带偏。

## 批次 2：读长文时目录滚没了（用户报的真 bug）+ 两条测试工具假断言

### 现象与根因

用户报：「读文章时候下滑目录会看不到」。用 CDP 量几何，确认是真的：

```
原布局（文章 2605px / 视口 804px）
  scrollY=  0  目录 top= 279   可见
  scrollY=400  目录 top= -81   可见（刚好在边缘）
  scrollY=800  目录 top=-481   ❌ 滚没了
  scrollY=1500 目录 top=-1181  ❌
  scrollY=2227 目录 top=-1908  ❌   ← 文章后半段完全看不到目录
```

根因是**对 `position: sticky` 的一个常见误解**：`top` 只在**父元素高度范围内**生效。
当时的 DOM 是

```html
<aside class="absolute -right-64 top-10 ...">        <!-- 高度 = 目录自己：203px -->
  <div class="sticky top-24 ...">目录</div>           <!-- 只有 203px 的活动范围 -->
</aside>
```

`sticky` 的父元素是那个 `aside`，而 absolute 定位让它 `height` 收缩到内容高度（实测 203px）。
于是「粘住」只在 203px 内成立，滑过 400px 后它就被父元素的底边带走了。

### 修法

把「正文 + 绝对定位 aside」换成**两列 flex**，让 sticky 的包含块变成整个正文区：

```html
<div class="flex gap-8">
  <div class="min-w-0 flex-1 pt-8"><MarkdownRenderer /></div>
  <aside class="hidden w-56 shrink-0 xl:block">
    <div class="sticky top-24">目录</div>
  </aside>
</div>
```

实测修正后（同一篇文章、同一视口）：

```
  scrollY=353…1411  目录 top=96    ← 一直贴在视口顶（24 = 96px）
  scrollY=1763      目录 top=-178  仍部分可见
```

### 顺带去掉了 `max-height`（一个反直觉的取舍）

原实现是 `max-h-[calc(100vh-8rem)] overflow-auto`。对**长目录**这是个陷阱：
容器被压到视口高度后，粘住时容器底边算出来大约在视口底边**之上**，
末尾几项既不在视口里、用户也很难想到去滚侧栏（JS 会把末项滚进来，但人不知道）。

保持自然高度后，sticky 容器比视口高时会按「底部对齐」整体露出，最后一项也就可达。
实测（18 个标题、目录 741px、视口 804px）：

```
带 max-height：末项在 2299…3832 全程"不在视口内"，只有 4598 处才露出来
去掉 max-height：末项在 4598 处进入视口  → 可达 ✅
```

### 如实记录的已知边界

评论区在正文区**之外**，所以滚到最后约 15%（点赞区往下）时容器到底，目录仍会被带走。
这与页首标题区造成的起始偏移同源，是**当前 DOM 结构的固有边界**。
要连评论区一起吸住，得把评论区也挪进 flex 的左列（会改一大段模板），本轮没做 ——
但用户报的「读文章时看不到目录」已经解决（正文全程可见）。

### 新增回归断言 E7f（这条 bug 没有任何测试守着）

`tools/full-check.mjs` 新增：

```
✅ E7f 侧栏吸住：读长文时目录始终可见（sticky 的父元素必须撑满正文区）
   — 正文 7772px / 视口 1200px；25% 处 top=96，40% 处 top=96，55% 处 top=96；全部可见=true
```

判据取的是**几何**（正文中段三个位置上目录的 `top` 是否仍贴在视口顶部），
不是「class 里有 `sticky`」—— 当时类名完全正确，错的是布局模型，
所以任何基于类名的断言都守不住这条。

### 又发现一条假断言：`smoke-check` 的「按配置条数比按钮个数」

改完布局跑 smoke，从 44/44 掉到 **43/44**，红的这条失败信息是：

```
❌ 电梯栏「联系站长」与站点配置一致 — 配置可用 2 条（应渲染图 1 张、复制按钮 2 个）
   → 按钮 1 个；点击展开=true 图=1 复制=2 Esc 关闭=true
```

**渲染完全正确**（按钮 1、图 1、复制 2、Esc 正常），是断言写错了：

```js
contact.configured === contact.buttons   // 2 === 1 → 红
```

整个弹层只有**一颗**入口按钮，配 1 条和配 2 条都渲染 1 个。
这条断言只在「恰好配 1 条」时成立 ——

- 配 0 条时靠 `buttons === 0 ||` 的短路分支绕过；
- 配 2 条时直接红。

改成 `contact.buttons === (contact.configured > 0 ? 1 : 0)` 之后：
配 0 条断言 0 个、配 N 条断言 1 个，两个方向都仍然能红。

顺带说明：那次之所以会「配 2 条」，是因为我在诊断 E6a 时往演示库 PATCH 了测试数据
（`E2E 微信` + `qq`），跑完已清回 `[]` —— **诊断用的写入必须清理干净**，
否则「配置为空 → 按钮不渲染」这条验收在演示环境里就失去意义了。

## 批次 3：正文区域太窄（用户报）——加宽正文列 + 对齐参考站排版

### 现象与定性

用户反馈「正文区域好窄」，并给了参考站
`https://xn--ygr25xpohxwz.com/zero-to-fullstack/lessons/module-3-1/`。

用无头浏览器把两边的排版参数都量出来（视口 1440×900）：

| 指标 | 我们（改前） | 参考站 | 差 |
|---|---|---|---|
| 外层容器 | 1120px | 1407px | −287 |
| **正文列宽** | **444px** | **873px** | **−429（不到一半）** |
| 正文字号 | 16px | 18px | −2 |
| 行高 | 28px（1.75） | 34.2px（1.9） | — |
| **一行中文字数** | **27 字** | **45 字** | **−18** |
| 目录宽度 | 224px | 272px | −48 |

参考站在 1280 / 1440 / 1920 三个视口下正文都是 872–880px、45 字，即**固定列宽 + 大留白**，
不随视口拉伸 —— 这个行为照抄。

**根因是批次 2 我自己引入的**：为了让目录 sticky 生效，我把两栏 flex 塞进了
`max-w-content`（700px）的 `<article>` 里 —— 700 减去目录 224 与间距 32，正文只剩 444px。
**「通栏宽度」在两栏布局里不再等于「正文宽度」，而 `max-w-content` 这个 token 是按通栏调的。**

一个容易踩的点：**不能直接改 `max-w-content`** —— 它被 **9 处**共用
（关于页 / 留言板 / 友链 / 404 / 首页窄屏分支 / 崩溃页 / 详情页骨架屏与错误态…），
所以给详情页单独加了一个刻度 `maxWidth.article`。

### 改动

| 文件 | 改动 |
|---|---|
| `frontend/tailwind.config.js` | 新增 `maxWidth.article: '1280px'`；typography 的 `DEFAULT.css` 加 `fontSize: '18px'`、`lineHeight: 1.75 → 1.85` |
| `frontend/src/styles/components.css` | 新增 `.article-column`（`w-full max-w-[760px]`）—— 4 处以上复用，按 STYLEGUIDE 提到公共层 |
| `frontend/src/views/ArticleDetailView.vue` | `<article>` 改 `max-w-content xl:max-w-article`；两栏 `gap-8 → gap-14`；正文列 `.article-column`；目录 `w-56 → w-64`；**标题区 / 上下篇 / 相关阅读也套 `.article-column`** |
| `tools/full-check.mjs` | 新增 **E7g**（正文列宽与行宽的几何断言） |

**为什么 `<article>` 写成 `max-w-content xl:max-w-article`**：xl 以下没有目录列，
容器若还是 1280px，正文会拉满到 1000px 以上（≈55 字/行，过宽）。
双档写法让 1279 及以下自动回落到 `max-w-content`。

**为什么标题区 / 上下篇 / 相关阅读也要限宽**：`<article>` 现在是 1072px 的两栏容器，
这些区块若跟着撑满，会比正文宽 300px，一眼看上去是散的。评论区**刻意不限宽**
（表单有三个输入框，宽一点更好用），代价见文末「尚未做的」。

### 新增 E7g（这条 bug 的几何守门人）

「感觉正文好窄」这类问题**只有量出来才守得住**。判据刻意不硬编码字号：

```
一行字数 = 列宽 / 实测单字宽     ← 用 span 量「一个汉字多宽」，字号或字体一变比值就跟着变
断言：列宽 ∈ [740, 900] 且 一行 ∈ [38, 46] 且 xl 以上目录列存在且 ≥ 200px
```

实测输出：

```
✅ E7g 1440px 视口：正文列 760px、单字 18px → 一行 42 字；字号/行高 18px/33.3px；目录 256px（可见=true）
```

### 踩坑：改 `tailwind.config.js` 会把 Vite dev server 打崩，而且会静默写不进去

第一次改这个文件后，dev server 直接退出：

```
Error: EBUSY: resource busy or locked, watch
  '...\.tailwind.config.js.28108.0c3a534e-....tmpdir\tailwind.config.js.tmp'
```

Tailwind 在配置变更时会写一个临时目录，Vite 的 watcher 去 watch 它时撞上锁。

**更隐蔽的后果**：dev server 挂着时，写这个文件会**静默失败**
（`ReplaceFileW EIO (Win32 32)`），而同一批里的另一处编辑（`maxWidth` 段）已经落盘 ——
于是出现「配置看着改了一半、字号却不生效」的假象，我一开始还以为是 tailwind 不认 `fontSize`。

**判定方式**：不相信编辑返回值，直接读文件用正则确认（`/fontSize: '18px'/`），
或检查生成产物里有没有那条规则。**正确顺序：先停 dev server → 改配置 → 起 dev server。**

### 关键发现 1：4 张图是真丢了，而且旧站早就坏了

`FastAPI框架.md` 引用的 4 个「截屏2022-08-*」文件：磁盘没有、`public/`（构建产物）没有、

### 关键发现 2：新站的安全渲染策略决定了这不是「文件搬运」而是「内容归一化」

`frontend/src/utils/markdown.ts` 出于防钓鱼**刻意禁掉了 `style` 属性**
（内联样式能在正文里伪造全屏「登录框」），`class` 也只放行 `language-*`。
所以旧站那些 `<img style="zoom:50%">`、卡片阴影、居中说明文字导入后会**全部退化成裸标签**。
逐项处理：

| 旧站写法 | 处理 | 原因 |
|---|---|---|
| `<img style="...">` ×54 | 整体改写为 Markdown 图片 | 留着标签只会得到「标签还在、样式没了」 |
| `<img alt="...">` | **保留 alt** | 它是这张图唯一的文字语义 |
| `<p style="text-align:center">说明</p>` ×1 | 整行改 `*说明*`；与上一张图 alt 相同时**删除该行** | 否则退化成普通小字，看不出是图注 |
| `<font color=...>` ×1 | 保留（文本仍在，只是不再是红色） | 为一行加转换规则不如如实记录 |
| 围栏代码块内的 `<img>` | **逐字节不动** | 那是代码示例，改了就是篡改内容 |

### 关键发现 3：标题层级必须整体下沉，不能只改 H1

旧站 9 篇用了 `#`。新站现有文章的顶层是 `##`（标题由页面页头承担）。规则：

- H1 与文章标题**逐一字符相同**（忽略空白标点）→ 删除该行；
- 其余 H1 → 降为 `##`，并把全文标题**整体下沉一档**。

**为什么不能只把 H1 改成 H2**：反例是「培训」一文（两份独立笔记合在一个文件里，有两个 H1）。
只改 H1 会得到 `H2 子文章 → H3 着装原则 → H4 十条细节`，而目录只收录 H2~H4 且**按层级缩进**，
于是 H3 被过滤、10 个 H4 悬空显示。整体下沉后是完整三级，目录正常。

**代价是真实的**：`FastAPI框架` 与 `langchain与rag` 里原本最深的 H4 会变成 H5，超出目录收录。
它们是「章下面的三级小节」，旧站目录同样不显示——层级有语义，不为目录好看来压缩。

### 关键发现 4：图片 URL 绝不能自己拼（差点造成全站 404）

第一版试跑「成功」了：文章建好、图片上传、14 条附件记录。但逐条测 URL 时
**14/14 全部 404**。

根因：服务端按 `uploads/<YYYYMM>/` 分目录落盘（`AttachmentService.upload`），
而导入器自己拼了 `/media/uploads/{name}`——**少一层月份目录**。
最危险的地方在于**整个过程没有任何报错**，只有打开文章看图才会发现。

修法：URL 一律取 `POST /attachments/upload` 响应里的 `url`，导入器不再自己拼；
预检（不联网）用与 `AttachmentService` 同一套月份规则构造，保证两边一致。
教训：**能从接口拿的值就不要自己算**，尤其是路径。

### 关键发现 5：本地 slug 估算与服务端不一致 → 重跑会重复导入

导入器要「先用 slug 预判文章是否存在」以避免重复。第一版把规则写成
「删掉所有非字母数字汉字」，而服务端 `utils/text.slugify` 是
「把连续的非词字符替换成**一个连字符**」：

| 标题 | 服务端 | 我写的（错） |
|---|---|---|
| `算法竞赛C++STL常用用法` | `算法竞赛c-stl常用用法` | `算法竞赛cstl常用用法` |
| `二分查找、三分查找` | `二分查找-三分查找` | `二分查找三分查找` |
| `C++竞赛代码模板` | `c-竞赛代码模板` | `c竞赛代码模板` |

23 篇里 **5 篇对不上**，重跑就会把已存在的文章当成新文章再建一份。
修法：规则逐字符对齐，并加一条**跨仓一致性测试**——它直接 `import` 后端真正的
`slugify` 做交叉校验。这条测试立刻又抓出第二个差异：标题里一个有效字符都没有时
（如 `！！！`）服务端返回 `article-{随机8位}`，**随机的、本地不可能算出来**。
这类文章靠「标题完全相同」兜底（旧站 23 篇没有这种标题，有测试断言每篇都能算出可读 slug）。

### 踩坑记录（都是「不会报错、只会悄悄做错」的那类）

1. **`scan_lines` 返回的行不带换行符**。我在两处把它当 `splitlines(keepends=True)` 用，
   于是**整篇正文被拼成一行**。是测试抓到的——`test_normalize_deletes_only_that_line_not_neighbours`
   就是为这个写法准备的。修法：换行符从 `body.splitlines(keepends=True)` 按行号取。
2. **`<img>` 的边界不能只写 `\b`**：`\b` 只在「单词字符与非单词字符之间」成立，而 `-` 是非单词字符，
   所以 `<img-x>` 里 `img` 之后的 `\b` **照样成立**（`<image>` 同理）。
   必须 `(?<![-\w])<img(?=[\s/>])`。这条也是测试抓的。
3. **`\`\`\`html` 里的 `<img>` 是代码示例**，不是真图片。整个解析器因此做成围栏感知的逐行状态机，
   核心不变量是「围栏与行内代码的内容字节不变」，并由
   `test_real_repository_fences_are_never_rewritten` 对全部 23 篇断言。
   **反向验证过**：临时拆掉围栏保护后，示例代码确实被改坏、测试变红。
4. **GBK 控制台打印 ✅ 会崩**，而且崩在「打印成功消息」这一步——文章已经建好了，
   进程却以 `UnicodeEncodeError` 退出，看起来像导入失败。
   修法：启动时把 stdout/stderr 切成 UTF-8，切不动就把状态图标降级成 ASCII。
   （这也是为什么后来能直接在终端看到中文输出。）
5. **`POST /articles/manage/list` 的 `page_size` 上限是 50**，写 100 直接 422。
   这个值是从真实报错里量出来的，不是猜的。
6. **试跑数据必须先清干净再验证**。第一版试跑建的文章引用的是坏 URL；
   我用 API 删掉文章与附件（附件接口会连磁盘文件与变体一起清理）后重跑，
   才有「14/14 全部 200」这个可信结论。**不清就验，验的是脏数据。**

### 关键发现 6（最严重的一个）：Python 注释被当成 Markdown 标题改写

**最终核验**阶段做「逐篇全文比对」时发现：`FastAPI框架` 的正文比旧站**少了**两个空格，
并且 ```python 围栏里的两行从**单 `#` 变成了双 `##`**：

| | 内容 |
|---|---|
| 旧站原文 | `# response_model_include  `（行尾两个空格） |
| 导入后 | `## response_model_include` |

也就是 **Python 的注释被当成 Markdown 标题，跟着「整体下沉一档」一起被改了**。
代码被篡改，而页面上完全看不出来——它在代码块里，渲染出来就是两个井号。

根因：`normalize_headings` 的逐行循环里，我只写了 `if number in dropped`，
**漏掉了围栏判断**（更早的实现有 `if in_fence or number in dropped`，重写时丢了这个条件）。
`scan_lines` 本身判定完全正确（有测试断言它返回 `in_fence=True`），是调用方没用。

**为什么原有测试没抓住**：那条围栏用例是
``"# 标题\n\n```python\n# 这是代码注释\n## 也是注释\n```"``，断言 `"# 这是代码注释" in out`。
实测复核（临时探测脚本）显示输出里那行**确实变成了** `## 这是代码注释`，
但 `"# 这是代码注释"` **是它的子串**，所以 `in` 判定为真——**断言假通过**。

同一个坑当天已经踩过一次：`"## 一章" in "### 一章"` 也是子串，
当时改成了 `splitlines()` 精确比对，**但新写的围栏用例又犯了同样的错**。

修法与加固：
- 循环里显式构造 `fenced = {行号}` 并跳过（连行尾空白都不动）；
- 新用例 `test_normalize_does_not_touch_python_comments_in_fences` 用**真实事故文本**做断言：
  `"# response_model_exclude  \n" in out`（含行尾两个空格）**且** `"## response_model_exclude" not in out`
  ——两个方向都断言，这样"改多了"和"改少了"都能抓住；
- 新用例 `test_normalize_keeps_fenced_lines_byte_identical` 覆盖 7 种"看起来像标题"的围栏行
  （含 `#` 单独一行、`# ` 带尾空格、缩进的 `#`、以及带尾随空白的）；
- **三条变换路径全部反向验证**：临时拆掉围栏保护后 **8 条用例变红**
  （分别落在 `normalize_headings`、`merge_captions_into_alt`、`render_body` 三条路径上），
  确认测试真的守得住，而不是"刚好没被覆盖"；
- 修复后用 `--update` 重跑导入，把库里被篡改的正文写回正确内容。

**教训（比 bug 本身更值钱）**：`in` 做包含断言时，当心「期望值是实际值的**子串**」。
井号、编号、路径前缀这类文本最容易中招。断言**有前缀关系**的文本时，
一律用 `splitlines()` / `==`，或者**同时断言"不该出现的形态"**，不要只用一个 `in`。

### 关键发现 7：置顶必须远少于每页条数，否则头条机制失效

旧站 `sticky` 有值的 16 篇（占内容 70%）最初被全部映射成布尔置顶。
实测首页第一页 **10 张卡片全部挂「置顶」徽标**——这个信号等于失效。

原因不止是"数量多"：前台列表默认 `top_first=True`（`Article.is_top` 优先），
而首页把**第一篇渲染成 featured 头条**、其余进「更多文章」区，每页默认 10 条。
所以置顶数必须**远小于每页条数**。

最终取值：`sticky >= 24` → 保留 **3 篇**迁移文章为置顶（旧站权重 27/24/23 那几篇长篇教程），
加上演示数据原有的 2 篇共 4 篇；首页呈现为「4 条置顶 + 6 条普通 + 头条区与更多文章区都在」。

原始权重写进每篇的迁移尾注（`旧站排序权重 sticky: N`），
所以「哪几篇被保留为置顶」这个取舍是**可追溯、可反悔的**。
阈值做成了 CLI 参数 `--top-threshold`（`0` = 不设阈值，即全部保留），
并且这个判定在导入器里（不是事后手改脚本），所以**重跑幂等**。

一开始我是用手改脚本调整的，结果下一次 `--update` 重跑就把改动覆盖了——
这也是「能进导入器的逻辑就不要放在事后处理里」的一个实例。

### 关键发现 8：分类名大小写重复（首页侧栏一眼看出）

看首页截图时发现分类侧栏同时列着 **`Python` 和 `python`**——旧站 frontmatter 里写的是小写
`python`，演示数据里是 `Python`，而分类名是**大小写敏感**的，于是"同一个分类"出现两个。
一并合并（把 `python` 下的文章改挂到 `Python`，再删掉多余项），分类从 20 个降到 19 个。

这类问题只有**看渲染结果**才会发现：接口、测试、数据校验全都不会报错，
因为它压根不算错——只是丑。
**这也是为什么最后还要用真实浏览器核验一遍，而不是只跑测试。**


### 环境问题：本机 SQLite 建不出临时文件（与本次迁移无关，但必须记录）

验证时发现 `e2e_live` 的 A08（删文章 + 级联删评论）稳定失败，报
`sqlite3.OperationalError: unable to open database file`，失败的 SQL 是 `DELETE FROM articles`。

逐层排除，每一步都有实测证据：

| 检查 | 结果 |
|---|---|
| 换进程直连同一个库删同一行 | **成功** → 不是数据/库结构问题 |
| 用 HEAD **未改动**的 `e2e_run.py` 跑 | **同样失败** → 与我的改动无关（既有问题） |
| `os.access(dir, W_OK)` | `True` |
| 真的往该目录写文件 | **`PermissionError: 拒绝访问`** → `os.access` 在撒谎 |
| 在 `.pytest-tmp` 里做级联删除（各种 `journal_mode`） | **全部成功** |
| 在 `C:\Users\...\AppData\Local\Temp` 里建库 | **连库都建不出来** |
| 用应用连接的**简单**两表级联删除 | 成功 |
| 用应用连接删**真实 article**（多子表级联 + FTS 触发器） | **失败** |
| 先手动删子表再删主表 | **成功** → 确认是「需要临时表协同多个子表的级联」这一步 |

结论：本机 `TEMP` 指向的目录**可写普通文件、但 SQLite 建不出临时文件**，
于是任何需要临时表的语句（**级联删除、`ORDER BY` 溢出排序、`CREATE INDEX`**）都失败。
`PRAGMA temp_store` 默认是 `0`（跟随编译默认，即磁盘），踩不踩得到完全取决于环境。

**仓库早就为此预留了出口**：`Settings.sqlite_temp_store`（`session.py` 的注释里写着
「某些环境里 SQLite 建不出磁盘临时文件，任何需要临时表的语句都会直接报
`unable to open database file`」）。用文档化的方式打开它：

```bash
SQLITE_TEMP_STORE=MEMORY make test      # 以及 e2e-live
```

打开后：`pytest` 全绿、`e2e_live` **64/64**（A08 通过），根因得到确认。

**我一度改过 `conftest._safe_temp_dir()`**（加了一个真实跑级联删除的 SQLite 能力探测），
但实测**.pytest-tmp 上依旧失败**，说明它不解决问题、只增加 40 行复杂度——
已 `git checkout` 撤销，不让它混进这次迁移的 diff。

## 批次 5：正文滚动与目录滚动「相互独立」（用户提问「想清楚再告诉我」）

用户问的是「正文的滚动和目录的滚动能不能相互独立」。**先拆题再动手**，因为这句话有两种含义，
而且实测发现现状比问题本身更糟。

### 先拆题：当时目录根本没有自己的滚动

| 实测项 | 结果 |
|---|---|
| 目录 `overflow-y` | `visible` |
| `scrollHeight / clientHeight` | **相等**（测过两篇：短目录 173/173、E2E 造数 262/262）⇒ **自身完全不可滚** |
| 所以"不独立"的真相 | 不是两种滚动打架，而是**缺了一种滚动** |

### 问题 1：目录比视口高时，底部永远够不到

`fastapi快速入门自我总结`（70 个标题）实测：目录高 **1990px**、视口 900px。
多出来的 1000 多像素既不在视口里，目录自身又不可滚 —— 想看「第 12 章」只能**滚正文**。

### 问题 2：`sticky` 的包含块在文章 90% 处就结束了

祖先链实测（`fastapi框架`，文档总高 9972px）：

```
nav     static   文档 213→1312
div     sticky   文档 213→1312
aside   static   文档 213→8940   ← 包含块到此结束
article static   文档 105→9652   ← 文章本体
```

**包含块在 8940 结束、文档到 9972**，差的约 1000px（评论区那一段）里目录会被父容器带走。
这解释了为什么"调 `max-height`"解决不了：`top:96` 只在包含块范围内生效。

### 实测了 7 个方案，只有 `fixed` 全程达标

| 方案 | 自身可滚 | 尾部仍吸住 | 末项可达 |
|---|---|---|---|
| ① 现状 | ❌ | ❌ | ❌ |
| ②/④ `max-height + overflow` | ✅ | ❌ | ✅ |
| ⑤/⑥ 延长包含块（`min-height` / `align-items`） | ✅ | ❌ | ✅ |
| **⑦ `position: fixed`** | ✅ | **✅** | **✅** |

改前→改后（1440×900，长文）：

| 位置 | 改前（sticky） | 改后（fixed） |
|---|---|---|
| 25% | top=96 bottom=1259 ❌ 超出视口 | top=96 bottom=868 ✅ |
| 55% | top=96 bottom=1658 ❌ | ✅ |
| 95% | top=88 bottom=2077 ❌ | ✅ |
| 100% | top=−2122 **完全滚没** | ✅ |

正文列宽改前改后都是 **760px**。

### 落地：三层职责分离

```css
.toc-panel      { position: fixed; top: 6rem; left: max(...); width: 16rem; }
.toc-panel > nav{ max-height: calc(100dvh - 8rem); overflow-y: auto; overscroll-behavior: contain; }
```

**高度与滚动必须加在 `<nav>` 上，不能加在 `<aside>` 上** —— 这是本轮第一个真缺陷（见下）。

### 踩坑 1：把 `overflow` 放在 `aside` 上，会让「高亮自动滚入」静默失效

`TableOfContents` 的自动滚入判据是 `root.scrollHeight > root.clientHeight`，
而 **`root` 就是那个 `<nav>`**（组件模板 `ref="root"`）。
把 `overflow-y: auto` 放在外层 `aside` 上之后，滚动容器变成了 aside，
`nav` 不再是滚动容器 ⇒ 那条判据**恒为假** ⇒ 激活项滚出可视区后没人把它带回来。
实测征兆是目录 `scrollTop` 恒为 0。

改到 `<nav>` 上之后实测（滚到底 ↔ 回顶）：
`navScrollTop 1275 → 434`，同时**页面 scrollY 纹丝不动** —— 这才是用户要的「独立」。

### 踩坑 2：`fixed` 让目录跑到正文**左边**（差 760px）

`position: fixed` 之后元素脱离 flex 流，正文列把那 256px 吃了，
于是 `aside` 的**静态位置**（`left:auto` 的解析依据）落到整行的左边缘：

```
正文右 939 | 目录左 179 | 间距 -765
```

`margin-left: auto` 也救不了（静态位置同样按脱离流之后算，实测仍是 179）。
修法是显式给 `left`，取值由页面里的真实数字解出：

```
文档宽 1430（10px 竖向滚动条），行 179→1251，正文右 939，目标间距 56 ⇒ 目录左应为 995
fixed 的 50% 相对文档宽 = 715 ⇒ 常量 = 995 - 715 = 280
```

再配 `max()` 兜住窄 xl：1280 视口下文章受 `max-w-article` 限住，
只给 `50% + 280` 会把目录推出屏幕，所以取「对齐正文右边缘 + 56」作下限。

实测（四个视口）：间距恒 **56**、正文列恒 **760**、无重叠：

```
1280 → 正文右 859 目录左 915   1440 → 939 / 995
1920 → 1179 / 1235             2560 → 1499 / 1555
```

### 踩坑 3：我先前那次「验证通过」是假的

在注入 CSS 做方案对比时，我得到过「四个视口间距精确 56px」的结论并据此判断 `fixed` 零代价。
**那是错的** —— 探针量到的是注入生效前的旧元素位置（`aside` 仍是 flex item，本来就在右边）。
真正落地后再量才发现目录跑到了左边。

教训：**验证必须量「改动真正生效之后」的状态**。注入式对照要么先断言注入生效
（比如读一条只有新规则才有的计算样式），要么就别拿它当证据。

### 踩坑 4：E7h 第一版把三条既有用例弄红了

为守这个 bug 新增了 **E7h**。第一版犯了两个错：

1. **前提错误**：把「目录必须可滚」断言在 `E2E-目录长文` 上，而那篇只有 11 个标题
   （H2×3 + H3×3 + H4×5），展开到不动点实测 **233px**，在 1200px 视口里**永远不可能滚动**。
   怎么改都是红的。→ 改成只断言与目录长度无关的两件事（面板不漂移 + `overscroll` 是 `contain`），
   长目录可滚性由 E7f 承担（它用的长文目录实测 1163~1990px，不可滚时 `bottom` 会冲出视口）。
2. **污染后续用例**：E7h 为了测滚动要展开目录，而 `E7a/E7b/E7c` 断言的正是"默认折叠状态"
   （实测可见 7 条）。E7h 结束后没复位 ⇒ 三条一起红（E7a 拿到 8 条）。
   → 最终版不展开目录，于是不改变折叠状态，也就不必复原。

另外**顺手补了一个既有的顺序耦合**：E7h 之外，我还给 E7f 加了 `95%` 与 `100%` 两个采样点
（原来只测 25/40/55 三个中段位置 —— 而包含块失效只发生在文章尾部，正好绕开了）。
但滚到 100% 会把激活项带到文章最后一节，`revealActive` 于是展开它的祖先分支，
E7a 再拿到 8 条。⇒ 在 E7a 之前显式 `goto(ARTICLE)` 重新进入，
让「默认折叠状态」回到确定值。**该段本来就是个新用例族，从干净状态开始才是它应有的前提。**

### 我自己犯的一个判据错误（值得单独记）

E7h 里我写过 `Math.abs(deepTop) <= 4`，认为面板上边缘应该接近 0。
**面板的设计值是 `top: 6rem` = 96px** —— 96 永远不会 ≤ 4，这条断言**恒假**。
更糟的是我把 `>=` 看成了 `<=`，一度得出「`Math.abs(96) > 4` 在 JS 里返回 true、运行时被篡改」
这种荒唐结论，浪费了一轮排查。

正确判据是**「与滚动位置无关」**：面板 top 在若干个不同 scrollY 下必须完全相同。
最终版就是这么写的（实测 `tops = [96,96,96,96]`，`pinned=true`）。

教训：**断言"钉住"要看"是否随滚动变化"，不要跟某个绝对常数比**；
以及读自己的代码时，`<=` 和 `>=` 值得停下来确认一次。

### 顺带加固的既有断言

`E7f` 原来的可见性判据是 `bottom > 0 && top < innerHeight`（**碰到视口就算过**）——
下限太松：目录高 1990px 而视口 900px 时它依然成立，被裁掉一半也照样绿。
改成 `fullyVisible`（`top >= 0 && bottom <= innerHeight`），并补上 95%/100% 采样。

## 批次 6：首页「分类」也能独立滚动（用户要求）

用户说「首页的分类也要能够独立滚动」。批次 5 解决的正是**目录**的同类问题，
所以这里先量数据再决定改哪一层。

### 先看现状：首页侧栏比视口还高，而且原因和目录那个 bug 同源

实测（1440×900，首页）：

```
aside          高 1075px   预算只有 772px  →  超出 303px，且 overflow: visible
  分类卡        530px（13 条，列表 464px）
  标签卡        327px
  快捷入口      170px
```

- **侧栏自身不可滚**（`overflow: visible`），所以超出的 303px 无从到达
- 「快捷入口」在首屏**被截掉**（基线实测 `快捷入口完整可见 = false`）
- 顺带确认了一件事：侧栏的包含块是 `DIV.grid`（文档 105..2336），
  sticky 可用范围 **1165px**，而页面只滚 **1757px** ——
  滚动窗口 795px **完全落在**可用范围内，所以侧栏在整段滚动里都能吸住
  （实测页面中段 `aside top = 96`）。它不是批次 5 那个"被父容器带走"的问题。

### 决定改哪一层：两个方案，用数据选

| 方案 | aside 高 | 是否装进视口 | 分类可滚 | 标签/快捷入口 |
|---|---|---|---|---|
| 现状 | 1075 | ❌ 超 303 | ❌ | 快捷入口被截 |
| **A 只让分类列表滚** | **931** | ❌ 超 159 | **✅** | 两张卡都常驻可见 |
| B 让整个侧栏滚 | 772 | ✅ | ❌ | 会被滚出视野 |

起初我想选 B（scrollbar 落在侧栏边缘，更好看，且侧栏能完全装进视口）。
但 B 有个更实际的代价：**标签与快捷入口会被滚出视野** —— 侧栏 1075px 里
它们在最下面，等于把「看得到但够不到」换成了「够得到但看不到」。
而 A 正好是用户要的形态（分类独立滚动），标签与快捷入口保持常驻。
**选 A。**

### 高度上限怎么定：不用拍脑袋的数字

反推过一版「让整张分类卡装进视口」的预算：

```
804（视口可用）− 545（标签 327 + 快捷 170 + 两处间距 48）− 64（卡片内边距 + 标题）
= 195px ≈ 5 项（实测每项 32px + 间距 4px）
```

5 项太局促，所以不追求"整栏装进视口"，只给分类列表一个有依据的上限：

```html
<ul class="max-h-[min(20rem,calc(100dvh-30rem))] space-y-1 overflow-y-auto overscroll-contain pr-2.5">
```

- **`min(20rem, 100dvh − 30rem)` 而不是写死数字**：侧栏上下夹着固定高度的卡片
  （实测标签 327 + 快捷 170），死数字在矮视口下会把那两张卡挤出屏幕。
  按 32px/项换算：900px 视口 ≈ 7 项、1200px ≈ 10 项（13~19 个分类都能滚到）。
- **`overscroll-contain`** 与目录面板同一考量：列表滚到底后继续滑不把首页滚走。
- **`pr-2.5` 是给滚动条留位**：卡片内边距 16px + 条目自身 `px-3`(12px) = 28px，
  再留 10px，滚动条不会压在分类名或右侧的篇数上。

```

且 overflow-y ∈ {auto, scroll}

且 overscroll-behavior-y === 'contain'
```

第二、三条是关键：只断言"写了 max-h 类"的话，规则没生效、或上限大到不触发滚动，
照样能绿 —— 那正是这类改动最容易骗过测试的地方。

### 一个反直觉的发现：旧站页脚那行「时钟」不是时钟

`_config.fluid.yml` 的 footer 里挂着 `<span id="timeDate"></span><span id="times"></span>`
和一个 `/js/timeDate.js`。我一开始当成"当前时间"，读了脚本才发现**起点写死在脚本里**：

```js
var grt = new Date("11/14/2025 13:14:52");   // 建站时间
document.getElementById("timeDate").innerHTML =
  "FurinaLuna-Laboratory 自从搭建已经历" + dnum + " 天 ";
document.getElementById("times").innerHTML = hnum + " 小时 " + mnum + " 分 " + snum + " 秒";
```

所以它是**建站计时**，不是 `HH:MM:SS` 时钟。按真实语义迁移，
起点取脚本里那个 `2025-11-14 13:14:52 Asia/Shanghai`（写成 `+08:00` 偏移，不依赖机器时区）。

顺带不继承旧脚本的一个缺陷：它用 `Math.round` 算秒，
`Math.round(59.6) === 60` → 偶尔会显示「60 秒」。新版用 `Math.floor` 且先算天再算时分秒，
单测专门锁住 `59.6 秒仍应是 59` 这个位置。

### 改了一半的坑：站点名在三个地方各写死了一遍

这是本批次最有价值的发现。站点名此前**不是**一处常量，而是三处：

| 位置 | 写死的东西 | 后果 |
|---|---|---|
| `router/index.ts` 的 `afterEach` | `const base = '个人博客'` | 浏览器标签页永远显示旧名 |
| `composables/useHead.ts` 的 `SITE_SUFFIX` | `'个人博客'`，兼 `<title>` 与 `og:site_name` | 标签页与分享卡片都是旧名 |
| 同文件的 `DEFAULT_DESCRIPTION` | 「记录技术、生活，以及一切值得写下来的东西。」 | 每一页的分享描述都冒充站点描述 |

也就是说：**改 store 里的站名只改得动顶栏和页脚，标签页纹丝不动** ——
这正是"改一半等于没改"。修法是抽出 `composables/useSiteName.ts` 作为唯一来源
（`useSiteName()` + `useSiteDescription()`，兜底值也放在那里），三处都改成用它。

还有一处**必须响应式**：站点资料是挂载之后异步回来的，所以 `useHead` 的 watch
要把「页面 meta」与「站点名 / 兜底描述」一起作为依赖 —— 只监听 meta 的话，
首帧之后就再也没人修正 `<title>`、`og:title`、`og:site_name` 了。

### 页脚新增个人介绍与建站时长

- **个人介绍**：取 `bio_md` 的**首段**（先丢掉围栏代码块，再取第一个非空行，最后抹掉 `**加粗**`）。
  不用 `MarkdownRenderer`：页脚每页都渲染，为一行文字引入完整渲染 + 消毒管线不划算，
  而且渲染出的 `<p>` 嵌在 `<p>` 里是非法 HTML。完整内容仍由「关于」页承载。
- **建站时长**：新增 `components/SiteUptime.vue`，计算与格式化抽到 `utils/uptime.ts` 纯函数
  （单测覆盖边界），组件只负责每秒刷新。
  **每 1 秒从固定起点重算而不是给计数器 +1**：后台标签页被节流后回到前台会立刻跳到正确值，
  计数器会越走越慢。`onBeforeUnmount` 里清掉定时器 —— 页脚在每个页面都有，不清就是稳定的定时器泄漏。

### 顺带查出并修掉两条**陈旧断言**（interaction-check 24/25 → 25/25）

README 里原本把这条记作「已知失败」，我按用户要求核实到底，结果**不是产品问题、是断言写错**：

**① 成功文案断言与组件脱节**

```js
// 断言在找：
success: /评论已发布|等待站长审核/.test(text)
// 组件实际输出（CommentSection.vue:74）：
'评论已提交，等待站长审核后显示'
```

「等待站长审核」后面紧跟一个「后」，于是 `|` 的两个分支**都落空**。
评论其实提交成功了（条目 0 → 1、也没有错误提示），却常年报「成功提示没出现」。

**② 「有没有错误提示」把上一条用例的 toast 算了进来**

断言原本只看「**此刻**页面上是否存在错误文本」。而这一步前面跑的是后台评论审核，
那边的 toast 常常还没消失 —— 于是把**别人的提示**当成本次失败。
插桩实测拿到了决定性证据：

```
posted = {"before":0,"after":1,"success":true,"needApproval":false,"errorToast":true}
```

`success` 为真、条目也涨了，只有 `errorToast` 为真；而同一时刻把页面全文抓出来，
`/评论提交失败|过于频繁/` **一条都匹配不到**。修法是提交**之前**先记一份页面文本，
只认「**新出现**」的错误提示。修完 25/25。
