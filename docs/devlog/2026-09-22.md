## 批次 1 · 让 CI 真的能跑

### 起因：最强的那张回归网，恰好是唯一没被自动化的那条

审计给出的三条证据拼在一起才看出全貌：

1. `docs/ROADMAP.md` 第 0 节自己写着「远程 CI 因账号账单锁从未真正执行」——
   而 README 顶部挂着 CI 绿标；
2. `.github/workflows/ci.yml` 的 `e2e` 作业跑在 `ubuntu-latest`，步骤里包含
   `node tools/interaction-check.mjs`；
3. `tools/interaction-check.mjs:14` 把浏览器路径**写死**为
   `C:/Program Files/Google/Chrome/Application/chrome.exe`，且脚本开头就是
   `if (!existsSync(CHROME)) throw new Error('chrome not found')`。

也就是说：账单锁解除之后，这个作业仍然会在「交互验证」这一步失败；
而由于步骤失败会中断 job，紧跟其后的「全功能回归」（41 项，含数据基线核对）
**一步都不会跑**。所谓"最值钱的回归网"实际是离线状态。

### 改了什么

| 文件 | 改动 |
|---|---|
| `tools/lib/chrome.mjs` | 新增。跨平台探测 + 统一启动参数 |
| `tools/smoke-check.mjs` / `full-check.mjs` / `interaction-check.mjs` | 删掉各自抄的一份候选列表，改用上面的模块 |
| `tools/e2e_live/e2e_run.py` | `PY` 从写死的 `.venv/Scripts/python.exe` 改为 `sys.executable` |
| `.github/workflows/ci.yml` | 缓存键修正、pytest 带 `--cov`、新增 `e2e-live` 作业 |
| `backend/pyproject.toml` | `[tool.coverage.report] fail_under = 80` |
| `Makefile` | 新增 `e2e-live` 目标；补齐 `.PHONY` 漏掉的 `typecheck` / `migrate-down` |

浏览器探测的优先级：环境变量（`CHROME_PATH` / `CHROME_BIN` /
`PUPPETEER_EXECUTABLE_PATH`）→ 平台候选路径（Windows 含 `LOCALAPPDATA` 与 Edge，
macOS 含 Chromium/Edge，Linux 含 snap）→ `PATH` 查找。
**失败时把尝试过的位置全部打印出来**并给出覆盖方式。

### 为什么这么做（放弃的方案）

- **不用 Playwright/Puppeteer**：会往项目里塞几百 MB 浏览器依赖，而这个仓库
  刻意选择了"CDP + 系统浏览器"路线（`spawn` + Node 22 内置 WebSocket）。
  审计的建议是"改候选路径"，不是"换工具"，保持原路线不动摇。
- **不无条件加 `--no-sandbox`**：很多 CI 教程这么写，但它会削弱沙箱。
  这里只在 `process.getuid?.() === 0`（真的以 root 跑，比如容器里）时追加，
  GitHub runner 是非 root，不需要它。
- **不给 `pip-audit` 钉版本**：job 里原有注释说明"安全扫描器需要最新漏洞库"，
  虽然钉住 pip-audit 并不会影响它拉取公告库，但那是另一个话题——
  无充分理由不动既有取舍。
- **PG 方言暂时不塞进 `e2e-live` 作业**：`e2e_run.py` 的 PG 模式依赖
  `docker exec … psql`（面向本地 compose 栈），直接搬进 CI 需要重构。
  改用更划算的组合：`backend-postgres` 作业让**整个 pytest 套件跑在真 PG 上**
  （下一批次落地），覆盖面比 61 条 e2e 更宽。

### 怎么验证的

先起一套独立环境（**不碰 `backend/blog.db`**，用临时库 + 演示数据，
与 CI 的环境变量一致）：

```bash
cd backend && DATABASE_URL="sqlite+aiosqlite:///./ci_e2e.db" \
  SEED_DEMO_DATA=true ADMIN_PASSWORD=admin123456 RATE_LIMIT_ENABLED=false \

cd frontend && npm run dev
```

| `node tools/interaction-check.mjs` | **22 / 22 通过** |

### 踩坑备忘

- **`existsSync` 失败的失败方式很隐蔽**：`smoke` / `full-check` 原本也有
  `/usr/bin/google-chrome` 候选，所以它们**在 Linux 上其实能找到浏览器**——
  真正卡住的是 `interaction-check`。三处代码长得几乎一样，只有一处是纯
  Windows 路径，靠"看起来都一样"是发现不了的，必须逐行比对常量。
- **步骤失败会吃掉后面的步骤**：如果只看到"交互验证失败"，很容易得出
  "环境缺 Chrome"的结论；实际连带后果是 41 项全功能回归从未运行。
  写 CI 时把"最强的一道防线"排在"最容易失败的一步"之后，是这次真正的教训。
- **`make` 在纯 Git Bash 环境里不一定存在**，验证时用手写的等价命令序列
  （ruff → format → import-linter → pytest --cov → tsc → eslint → vitest）。

## 批次 2 · 生产方言终于被测到了（PG 检索索引 + bcrypt 出循环）

### 起因一：整套测试从没在**生产用的那个数据库**上跑过

`docker-compose.yml` 里生产库是 `postgres:16`，而 `tests/conftest.py` 把
`DATABASE_URL` 写死成 SQLite。于是所有方言分支（外键级联是否真生效、枚举/布尔/
JSON 列怎么建、没有 FTS5 时检索走哪条路、迁移在 PG 上能不能跑）**全部零覆盖**。

批次 1 已经说明为什么不能简单地把 `e2e_run.py` 的 PG 模式搬进 CI（它依赖
`docker exec … psql`）。更划算的做法是给整套 pytest 加一条方言开关：

```bash
TEST_DATABASE_URL=postgresql+asyncpg://blog:blog@127.0.0.1:5432/blog_test pytest
```

CI 里对应新增 `backend-postgres` 作业（service 容器 + 真库）。

### 一开就跑出三个真问题

1. **`RuntimeError: Event loop is closed`（第二个用例开始全 ERROR）**。
   根因：asyncpg 的连接把 transport **绑在创建它的那个事件循环**上，而
   pytest-asyncio 默认每个用例一个新 loop。连接池里留着上一个 loop 的连接，
   下个用例拿到就炸。SQLite/aiosqlite 因为每次调用都取"当前运行的 loop"、
   不持有 transport，所以**只跑 SQLite 时这个坑永远看不见**。
   修法：`db_reset` 收尾 `await engine.dispose()` 归还连接。
2. **测试数据写超列长度**：`test_stats.py` 造 `ip_hash` 用
   `f"old{index:062d}"` = 65 字符，而列是 `String(64)`。SQLite 不校验 VARCHAR
   长度，悄悄存下了；PG 直接 `StringDataRightTruncationError`。
   这是**测试自己的 bug**，不是产品代码的——但没有 PG 这条路径就永远抓不到。
3. **搜索在生产方言上是全表扫描**（下一节）。

### 起因二：搜索在生产库上是"假加速"

`articles_fts` 是 SQLite 专有虚拟表，`fulltext_available()` 对非 SQLite 直接
返回 False，于是 PG 上搜索永远走
`title/summary/content_md ILIKE '%kw%'`——三列全表扫描 + 同条件 COUNT，
而 `/articles/search` 还不在限流名单里。

**方案选择：`pg_trgm` + GIN，不用 tsvector。**

| 方案 | 中文短查询 | 现有 SQL | 额外依赖 |
|---|---|---|---|
| `tsvector` + GIN | 需要 zhparser / pg_jieba，否则整段中文被当成一个 token（FTS5 的 `unicode61` 就是这个下场，迁移注释里有实测记录） | 要重写 | 扩展的扩展 |
| **`pg_trgm` + GIN** | 短查询同样救不了（见下），但 ≥3 字直接受益 | **零改动** | 一个 trusted 扩展 |

代价与边界（实测，不是估计）：

| 语料 | 关键词 | 计划器选索引？ | 耗时 |
|---|---|---|---|
| 500 篇 | 任意 | 否 | ~1.4ms（顺序扫描本来就够快） |
| 5000 篇 | 任意 | 否 | ~14ms |
| 50000 篇 | 「数据库设计实践」(7 字) | **是** | **6.6ms**（顺序扫描 181ms） |
| 50000 篇 | 「数据库设计」(5 字) / 「数据库」(3 字) / 「数据」(2 字) | 否 | 140–181ms |

结论写进文档时**没有夸大**：三元组索引的粒度决定了它救不了短查询——这与
SQLite 上 FTS5 的 trigram 分词器是同一条限制（所以服务层本来就有"<3 字退回
LIKE"的分流）。索引的真实收益是"长关键词在大语料上不再全表扫描"，
外加写入侧可忽略的成本（个人博客的写入量）。

**顺带补的那道闸**：`/articles/search` 现在限流 30 次/分。限流不解决单次查询
慢，但它把"脚本化的全表扫描"从不划算变成不划算得多——这比索引更直接地回应了
审计里"廉价放大攻击面"那条结论。

### 起因三：bcrypt 按住事件循环

`hash_password` / `verify_password` 是同步 CPU 调用（cost=12，实测 185ms/次），
而部署是单 worker（`--workers 1`）。一次登录 = 整个站点停摆 185ms；
`_dummy_hash()` 那条"抗用户名枚举"的等时校验同样在循环里跑。

修法：`security.py` 增加 `hash_password_async` / `verify_password_async`，
内部用 **标准库 `asyncio.to_thread`**——不用 anyio，因为它目前只是 FastAPI 的
传递依赖，直接 import 会引入幽灵依赖（仓库有 `test_dependency_lock.py` 在管
依赖卫生，这里遵守同一取舍）。

**怎么证明修好了**：写了一条"反面样本"探针，同一段计数逻辑分别跑同步实现与
线程池实现：

```
同步 bcrypt（反面样本）: 耗时 185ms，事件循环跳了 0 次
asyncio.to_thread 包装  : 耗时 199ms，事件循环跳了 13 次
```

0 与 13 的差距说明这条断言不是假绿：把实现改回同步，用例必然失败。
测试文件是 `tests/test_password_threading.py`（行为断言，不检查实现细节）。

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/db/fulltext.py` | 新增 `ensure_pg_trgm_indexes` / `pg_trgm_available` / `ensure_search_indexes`（按方言分流） |
| `backend/alembic/versions/20260922_1840_a7c1e9d4b2f8_*.py` | 新增迁移：PG 上建扩展 + 3 条 GIN；downgrade 只删索引**不删扩展**（托管 PG 常禁止 DROP EXTENSION，而"回滚必须能跑通"是硬要求） |
| `backend/src/app/api/deps.py` / `api/v1/articles.py` | 搜索端点限流 30/分 |
| `backend/src/app/utils/security.py` | 两个 async 包装 |
| `backend/src/app/services/auth_service.py` | 4 处调用点改走线程池 |
| `backend/tests/conftest.py` | `TEST_DATABASE_URL` 开关、PG 快路径（`create_all` + `TRUNCATE ... RESTART IDENTITY`）、每例 `engine.dispose()`、`sqlite_only` / `pg_only` 自动 skip |
| `.github/workflows/ci.yml` | 新增 `backend-postgres` 作业（真库 + PG 上跑迁移升→降→升） |

| `pytest`（真 PostgreSQL 16） | **456 passed, 1 skipped** |

| `ruff` / 格式 / import-linter | 全绿；契约 2 kept |

### 踩坑备忘

- **"第一个用例永远是好的"是事件循环绑定的典型症状**。看到 `ERROR at setup`
  从第二个用例开始，先怀疑 fixture 里的异步资源跨 loop 复用，而不是业务代码。
- **`enable_seqscan = off` 只能证明"索引可用"，不能证明"索引有用"**。
  我第一版探针只跑强制计划，差点把"2 字查询也能走索引"写进文档；
  补了默认计划的对照组才发现 PG 在小语料上（正确地）选择顺序扫描。
  **性能结论必须同时给"计划"和"耗时"，否则很容易自我安慰。**
- **PG 上每例 `drop_all + create_all` 要 1.6s**（442 例 ≈ 12 分钟）。
  改成 `create_all + TRUNCATE ... RESTART IDENTITY CASCADE` 后降到 8 分钟以内，
  语义仍是"空库 + 干净自增 id"。
- 迁移里 `downgrade` 不删扩展是**有意的**：RDS 之类的托管 PG 会直接拒绝
  `DROP EXTENSION`，那会让"回滚可用"这条契约在真实环境里失效。

## 今日学习清单

- GitHub Actions 的 `ubuntu-latest` 镜像自带 `/usr/bin/google-chrome`，
  所以"跨平台探测"不需要额外的安装步骤，只需要不写死路径。
- `--disable-dev-shm-usage`：容器与 CI runner 的 `/dev/shm` 常常只有 64MB，
  不加会随机崩在渲染上——表现是"用例莫名其妙挂了一条"，很难归因。
- `pytest-cov` 的 `fail_under` 只在带 `--cov` 时生效；写在配置里但 CI 不带
  `--cov`，等于门槛不存在（这正是本仓库此前 82% 覆盖率却没门槛的原因）。
- **asyncpg 的连接绑定事件循环，aiosqlite 不绑定**——所以"只在 SQLite 上跑过"
  的测试套件，永远发现不了跨 loop 复用连接池的问题。
- **SQLite 不校验 `VARCHAR(n)` 长度，PostgreSQL 校验**：同一份测试数据在
  两种库上的行为可以完全不同，而失败信息（`StringDataRightTruncationError`）
  指向的是"产品有问题"的错觉，实际是测试数据造错了。
- PG 13 起 `pg_trgm` 是 **trusted extension**，库 owner 就能 `CREATE EXTENSION`，
  不需要超级用户——这让"迁移里建扩展"在托管环境里也可行。
- 三元组索引救不了 1–2 字的 LIKE 查询：`%数据%` 里连一个完整三元组都提不出来。
  这与 FTS5 选 `trigram` 分词器后的限制是同一件事，两个方言在这点上**恰好一致**。
