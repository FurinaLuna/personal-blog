## 批次 1 · 让 CI 真的能跑

### 起因：最强的那张回归网，恰好是唯一没被自动化的那条

审计给出的三条证据拼在一起才看出全貌：

1. `docs/ROADMAP.md` 第 0 节自己写着「远程 CI 因账号账单锁从未真正执行」——
   而 README 顶部挂着 CI 绿标；
2. `.github/workflows/ci.yml` 的 `e2e` 作业跑在 `ubuntu-latest`，步骤里包含
   `node tools/interaction-check.mjs`；
3. `tools/interaction-check.mjs:14` 把浏览器路径**写死**为
   `C:/Program Files/Google/Chrome/Application/chrome.exe`，且脚本开头就是
   `if (!existsSync(CHROME)) throw new Error('chrome not found')`。

也就是说：账单锁解除之后，这个作业仍然会在「交互验证」这一步失败；
而由于步骤失败会中断 job，紧跟其后的「全功能回归」（41 项，含数据基线核对）
**一步都不会跑**。所谓"最值钱的回归网"实际是离线状态。

### 改了什么

| 文件 | 改动 |
|---|---|
| `tools/lib/chrome.mjs` | 新增。跨平台探测 + 统一启动参数 |
| `tools/smoke-check.mjs` / `full-check.mjs` / `interaction-check.mjs` | 删掉各自抄的一份候选列表，改用上面的模块 |
| `tools/e2e_live/e2e_run.py` | `PY` 从写死的 `.venv/Scripts/python.exe` 改为 `sys.executable` |
| `.github/workflows/ci.yml` | 缓存键修正、pytest 带 `--cov`、新增 `e2e-live` 作业 |
| `backend/pyproject.toml` | `[tool.coverage.report] fail_under = 80` |
| `Makefile` | 新增 `e2e-live` 目标；补齐 `.PHONY` 漏掉的 `typecheck` / `migrate-down` |

浏览器探测的优先级：环境变量（`CHROME_PATH` / `CHROME_BIN` /
`PUPPETEER_EXECUTABLE_PATH`）→ 平台候选路径（Windows 含 `LOCALAPPDATA` 与 Edge，
macOS 含 Chromium/Edge，Linux 含 snap）→ `PATH` 查找。
**失败时把尝试过的位置全部打印出来**并给出覆盖方式。

### 为什么这么做（放弃的方案）

- **不用 Playwright/Puppeteer**：会往项目里塞几百 MB 浏览器依赖，而这个仓库
  刻意选择了"CDP + 系统浏览器"路线（`spawn` + Node 22 内置 WebSocket）。
  审计的建议是"改候选路径"，不是"换工具"，保持原路线不动摇。
- **不无条件加 `--no-sandbox`**：很多 CI 教程这么写，但它会削弱沙箱。
  这里只在 `process.getuid?.() === 0`（真的以 root 跑，比如容器里）时追加，
  GitHub runner 是非 root，不需要它。
- **不给 `pip-audit` 钉版本**：job 里原有注释说明"安全扫描器需要最新漏洞库"，
  虽然钉住 pip-audit 并不会影响它拉取公告库，但那是另一个话题——
  无充分理由不动既有取舍。
- **PG 方言暂时不塞进 `e2e-live` 作业**：`e2e_run.py` 的 PG 模式依赖
  `docker exec … psql`（面向本地 compose 栈），直接搬进 CI 需要重构。
  改用更划算的组合：`backend-postgres` 作业让**整个 pytest 套件跑在真 PG 上**
  （下一批次落地），覆盖面比 61 条 e2e 更宽。

### 怎么验证的

先起一套独立环境（**不碰 `backend/blog.db`**，用临时库 + 演示数据，
与 CI 的环境变量一致）：

```bash
cd backend && DATABASE_URL="sqlite+aiosqlite:///./ci_e2e.db" \
  SEED_DEMO_DATA=true ADMIN_PASSWORD=admin123456 RATE_LIMIT_ENABLED=false \
  STORAGE_DIR="$TEMP/blog-verify-media" \
  ./.venv/Scripts/python.exe -m uvicorn app.main:app --app-dir src --port 8000
cd frontend && npm run dev
```

| 验证项 | 结果 |
|---|---|
| `node tools/smoke-check.mjs` | **34 / 34 通过** |
| `node tools/interaction-check.mjs` | **22 / 22 通过** |
| `node tools/full-check.mjs` | **41 / 41 通过**，数据基线一致 ✅ |
| `tools/e2e_live/e2e_run.py`（SQLite） | **PASS=62 FAIL=0 ERROR=0**，"项目真实库未被污染" |
| `pytest --cov=app` | 442 passed，覆盖率 **82.20%** ≥ 门槛 80% |
| `ruff check` / `ruff format --check` | All checks passed / 127 files already formatted |
| `scripts/lint_imports.py` | 2 contracts kept, 0 broken |
| `npm run type-check` / `npm run lint` / `vitest run` | 0 error / 干净 / 200 passed |

三个浏览器脚本这次是**在真实浏览器里跑完的**，不是只做语法检查——
改的是"怎么找到浏览器并启动它"，只有真启动一次才算验证。

### 踩坑备忘

- **`existsSync` 失败的失败方式很隐蔽**：`smoke` / `full-check` 原本也有
  `/usr/bin/google-chrome` 候选，所以它们**在 Linux 上其实能找到浏览器**——
  真正卡住的是 `interaction-check`。三处代码长得几乎一样，只有一处是纯
  Windows 路径，靠"看起来都一样"是发现不了的，必须逐行比对常量。
- **步骤失败会吃掉后面的步骤**：如果只看到"交互验证失败"，很容易得出
  "环境缺 Chrome"的结论；实际连带后果是 41 项全功能回归从未运行。
  写 CI 时把"最强的一道防线"排在"最容易失败的一步"之后，是这次真正的教训。
- **`make` 在纯 Git Bash 环境里不一定存在**，验证时用手写的等价命令序列
  （ruff → format → import-linter → pytest --cov → tsc → eslint → vitest）。

## 批次 2 · 生产方言终于被测到了（PG 检索索引 + bcrypt 出循环）

### 起因一：整套测试从没在**生产用的那个数据库**上跑过

`docker-compose.yml` 里生产库是 `postgres:16`，而 `tests/conftest.py` 把
`DATABASE_URL` 写死成 SQLite。于是所有方言分支（外键级联是否真生效、枚举/布尔/
JSON 列怎么建、没有 FTS5 时检索走哪条路、迁移在 PG 上能不能跑）**全部零覆盖**。

批次 1 已经说明为什么不能简单地把 `e2e_run.py` 的 PG 模式搬进 CI（它依赖
`docker exec … psql`）。更划算的做法是给整套 pytest 加一条方言开关：

```bash
TEST_DATABASE_URL=postgresql+asyncpg://blog:blog@127.0.0.1:5432/blog_test pytest
```

CI 里对应新增 `backend-postgres` 作业（service 容器 + 真库）。

### 一开就跑出三个真问题

1. **`RuntimeError: Event loop is closed`（第二个用例开始全 ERROR）**。
   根因：asyncpg 的连接把 transport **绑在创建它的那个事件循环**上，而
   pytest-asyncio 默认每个用例一个新 loop。连接池里留着上一个 loop 的连接，
   下个用例拿到就炸。SQLite/aiosqlite 因为每次调用都取"当前运行的 loop"、
   不持有 transport，所以**只跑 SQLite 时这个坑永远看不见**。
   修法：`db_reset` 收尾 `await engine.dispose()` 归还连接。
2. **测试数据写超列长度**：`test_stats.py` 造 `ip_hash` 用
   `f"old{index:062d}"` = 65 字符，而列是 `String(64)`。SQLite 不校验 VARCHAR
   长度，悄悄存下了；PG 直接 `StringDataRightTruncationError`。
   这是**测试自己的 bug**，不是产品代码的——但没有 PG 这条路径就永远抓不到。
3. **搜索在生产方言上是全表扫描**（下一节）。

### 起因二：搜索在生产库上是"假加速"

`articles_fts` 是 SQLite 专有虚拟表，`fulltext_available()` 对非 SQLite 直接
返回 False，于是 PG 上搜索永远走
`title/summary/content_md ILIKE '%kw%'`——三列全表扫描 + 同条件 COUNT，
而 `/articles/search` 还不在限流名单里。

**方案选择：`pg_trgm` + GIN，不用 tsvector。**

| 方案 | 中文短查询 | 现有 SQL | 额外依赖 |
|---|---|---|---|
| `tsvector` + GIN | 需要 zhparser / pg_jieba，否则整段中文被当成一个 token（FTS5 的 `unicode61` 就是这个下场，迁移注释里有实测记录） | 要重写 | 扩展的扩展 |
| **`pg_trgm` + GIN** | 短查询同样救不了（见下），但 ≥3 字直接受益 | **零改动** | 一个 trusted 扩展 |

代价与边界（实测，不是估计）：

| 语料 | 关键词 | 计划器选索引？ | 耗时 |
|---|---|---|---|
| 500 篇 | 任意 | 否 | ~1.4ms（顺序扫描本来就够快） |
| 5000 篇 | 任意 | 否 | ~14ms |
| 50000 篇 | 「数据库设计实践」(7 字) | **是** | **6.6ms**（顺序扫描 181ms） |
| 50000 篇 | 「数据库设计」(5 字) / 「数据库」(3 字) / 「数据」(2 字) | 否 | 140–181ms |

结论写进文档时**没有夸大**：三元组索引的粒度决定了它救不了短查询——这与
SQLite 上 FTS5 的 trigram 分词器是同一条限制（所以服务层本来就有"<3 字退回
LIKE"的分流）。索引的真实收益是"长关键词在大语料上不再全表扫描"，
外加写入侧可忽略的成本（个人博客的写入量）。

**顺带补的那道闸**：`/articles/search` 现在限流 30 次/分。限流不解决单次查询
慢，但它把"脚本化的全表扫描"从不划算变成不划算得多——这比索引更直接地回应了
审计里"廉价放大攻击面"那条结论。

### 起因三：bcrypt 按住事件循环

`hash_password` / `verify_password` 是同步 CPU 调用（cost=12，实测 185ms/次），
而部署是单 worker（`--workers 1`）。一次登录 = 整个站点停摆 185ms；
`_dummy_hash()` 那条"抗用户名枚举"的等时校验同样在循环里跑。

修法：`security.py` 增加 `hash_password_async` / `verify_password_async`，
内部用 **标准库 `asyncio.to_thread`**——不用 anyio，因为它目前只是 FastAPI 的
传递依赖，直接 import 会引入幽灵依赖（仓库有 `test_dependency_lock.py` 在管
依赖卫生，这里遵守同一取舍）。

**怎么证明修好了**：写了一条"反面样本"探针，同一段计数逻辑分别跑同步实现与
线程池实现：

```
同步 bcrypt（反面样本）: 耗时 185ms，事件循环跳了 0 次
asyncio.to_thread 包装  : 耗时 199ms，事件循环跳了 13 次
```

0 与 13 的差距说明这条断言不是假绿：把实现改回同步，用例必然失败。
测试文件是 `tests/test_password_threading.py`（行为断言，不检查实现细节）。

### 改了什么

| 文件 | 改动 |
|---|---|
| `backend/src/app/db/fulltext.py` | 新增 `ensure_pg_trgm_indexes` / `pg_trgm_available` / `ensure_search_indexes`（按方言分流） |
| `backend/alembic/versions/20260922_1840_a7c1e9d4b2f8_*.py` | 新增迁移：PG 上建扩展 + 3 条 GIN；downgrade 只删索引**不删扩展**（托管 PG 常禁止 DROP EXTENSION，而"回滚必须能跑通"是硬要求） |
| `backend/src/app/api/deps.py` / `api/v1/articles.py` | 搜索端点限流 30/分 |
| `backend/src/app/utils/security.py` | 两个 async 包装 |
| `backend/src/app/services/auth_service.py` | 4 处调用点改走线程池 |
| `backend/tests/conftest.py` | `TEST_DATABASE_URL` 开关、PG 快路径（`create_all` + `TRUNCATE ... RESTART IDENTITY`）、每例 `engine.dispose()`、`sqlite_only` / `pg_only` 自动 skip |
| `.github/workflows/ci.yml` | 新增 `backend-postgres` 作业（真库 + PG 上跑迁移升→降→升） |

### 怎么验证的

| 验证项 | 结果 |
|---|---|
| `pytest`（SQLite） | **452 passed, 5 skipped**（跳过的是 `pg_only`），覆盖率 **82.42%** ≥ 80% |
| `pytest`（真 PostgreSQL 16） | **456 passed, 1 skipped** |
| `alembic upgrade head → downgrade base → upgrade head`（PG） | 三步全通过；`pg_indexes` 里 3 条 `*_trgm`、`pg_extension` 里 `pg_trgm` 都在 |
| 迁移「降」之后 | 索引被删、扩展保留（刻意的） |
| 索引可用性 | `enable_seqscan=off` 下 `EXPLAIN` 出现 `Bitmap Index Scan on ix_articles_*_trgm` |
| 限流 | 第 31 次搜索 429 且带 `Retry-After`；列表接口刷 35 次不受影响 |
| `ruff` / 格式 / import-linter | 全绿；契约 2 kept |

### 踩坑备忘

- **"第一个用例永远是好的"是事件循环绑定的典型症状**。看到 `ERROR at setup`
  从第二个用例开始，先怀疑 fixture 里的异步资源跨 loop 复用，而不是业务代码。
- **`enable_seqscan = off` 只能证明"索引可用"，不能证明"索引有用"**。
  我第一版探针只跑强制计划，差点把"2 字查询也能走索引"写进文档；
  补了默认计划的对照组才发现 PG 在小语料上（正确地）选择顺序扫描。
  **性能结论必须同时给"计划"和"耗时"，否则很容易自我安慰。**
- **PG 上每例 `drop_all + create_all` 要 1.6s**（442 例 ≈ 12 分钟）。
  改成 `create_all + TRUNCATE ... RESTART IDENTITY CASCADE` 后降到 8 分钟以内，
  语义仍是"空库 + 干净自增 id"。
- 迁移里 `downgrade` 不删扩展是**有意的**：RDS 之类的托管 PG 会直接拒绝
  `DROP EXTENSION`，那会让"回滚可用"这条契约在真实环境里失效。

## 批次 3 · 正文能伪造全站浮层：消毒器的 class 绕过

### 问题

`utils/markdown.ts` 的消毒配置里，注释写得非常明确：

```ts
// 允许 data-*（代码高亮、任务列表都在用），但不允许 style ——
// 内联 style 可以做覆盖式钓鱼（伪造一个全屏"登录框"）
FORBID_ATTR: ['style', 'onerror', 'onload', 'onclick'],
```

但同一份配置的 `ALLOWED_ATTR` 里有 `class`。而**这个站点的工具类里就有**
`fixed inset-0 z-50 bg-white`（`ConfirmDialog.vue` 的遮罩）。于是作者在正文里
写一段裸 HTML，就能盖住整个页面并放一个密码框：

```html
<div class="fixed inset-0 z-50 bg-white flex items-center justify-center">
  <div><h2>登录已过期，请重新验证</h2>
  <input type="password" placeholder="请输入密码"></div>
</div>
```

威胁模型要说清楚：注入者是**已登录的作者**（`author` 角色），受害者是访客。
这不是"未授权 XSS"，而是"低权限角色伪造高权限界面"——正因为如此它容易被
忽略，但危害是实打实的钓鱼。

### 修法

| 面 | 之前 | 现在 |
|---|---|---|
| `class` | 整体放行 | 只放行 `language-*`（marked 为 ```lang 生成的声明） |
| `id` | 放行 | 不放行（正文不需要，标题锚点由渲染器自己生成） |
| `<input>` | 放行（含全部 type） | 只保留复选框（任务列表），其余整段删除 |
| 外链 `rel` | `/^https?:\/\//` 正则 | `new URL(href, origin)` 判同源（补上 `//evil.com` 这类协议相对地址） |

实现是 DOMPurify 的两个钩子（`uponSanitizeAttribute` 裁 class 值、
`afterSanitizeElements` 处理 input）。

### 踩坑备忘（这一批最值钱的部分）

1. **`forceKeepAttr` 是陷阱，不是救命稻草**。`class` 一开始被我从
   `ALLOWED_ATTR` 里删掉了，想让钩子"按白名单放行"。结果：`language-*` 也被丢，
   **代码高亮与语言角标全部失效**（既有的"代码块高亮"用例当场抓住，这就是
   回归测试的价值）。于是改用 `forceKeepAttr` —— 更糟：DOMPurify 里它是
   `continue`（"属性已获批，跳过后续检查"），而"把裁剪后的值写回 DOM"恰好
   在它**之后**，等于原样保留整个 class，`evil-class fixed inset-0` 一个没少。
   正确姿势是 **让 class 留在 `ALLOWED_ATTR` 里（属性本身合法），只用钩子改值**，
   由 `value !== initValue` 分支完成写回。
   结论：**钩子里改值和改"是否保留"是两条不同的路，混用会静默失效**。
2. **用探针脚本验证安全修复时，先确认探针本身是对的**。第一版端到端检查
   直接在全页 HTML 里 `grep 'inset-0'`，命中的是 Vite 注入的 CSS
   （`.inset-0 { inset: 0px; }`）和应用自身的 TOC 抽屉，于是报了假失败；
   第二版想"只取 `.prose` 容器"，自己写的 HTMLParser 提取器又因嵌套判断

## 批次 4 · 鉴权关键路径：别把"网络抖动"当成"你没登录"

### 问题：一条链路上叠了三个"把不确定当成确定"

审计里最重的一条前端问题是"守卫把 `/auth/me` 放在导航关键路径上"。
拆开看，它其实是三个独立缺陷叠在一起：

1. **网络失败被当成未登录**。`auth.restore()` 只在 401 时把 `restored` 置 true
   （那是**确定**答案）；网络失败时保持 false。而守卫的判断是
   `if (requiresAuth && !isAuthenticated) → 跳登录页` —— 于是"问不出来"
   和"你没登录"走了同一条分支，网络一抖，已登录的作者就被"登出"。
2. **公开页面也在等**。守卫的条件是
   `Boolean(to.meta.requiresAuth) || tokenStore.access !== null`，
   只要本地有 token 就 `await`。而这条链路是 20s 超时 + 400ms 退避重试一次，
   最坏能把"打开首页"按住几十秒。
3. **401 一律整页跳转**。`forceLogout()` 无条件
   `window.location.replace('/login?redirect=...')`。访客正在读文章，
   页面上任何一个后台请求（未读统计之类）401，整页就被弹走。

### 修法

| 场景 | 之前 | 现在 |
|---|---|---|
| 公开页面 + 本地有 token | `await restore()`（阻塞首屏） | 不等待，后台补一次 |
| 后台页面 + 网络失败 | 跳登录页 | **放行**（下次导航再试），页面自己表达失败 |
| 后台页面 + 恢复挂起 | 无限等 | 等，但上限 6s，超时放行 |
| 后台页面 + 401 | 跳登录页 | 跳登录页（这条是对的，保留） |
| 公开页面 + 401 | 整页跳登录页 | 只清凭证 + 通知 store |
| 有 access 无 refresh | 既不续期也不清凭证（死局） | 按凭证已死处理 |
| 完全匿名 + 401 | 未授权 | 未授权（**不能**说成"登录已过期"） |

两个实现要点：

- **`forceLogout` 怎么知道"当前页面需要登录"**：不能让 `api/http.ts` 直接 import
  router（会形成 `router → stores/auth → api/auth → api/http → router` 的循环）。
  用注入：http 层暴露 `setAuthRequiredProbe(fn)`，router 建好后把
  `() => router.currentRoute.value.meta.requiresAuth` 注册进去。
  顺带的好处是测试可以直接驱动这个行为，不用真挂一个 router。
- **清 token 之后谁来清 `user`**：`user` 是 store 里的内存状态，http 层拿不到。
  加一个单向信号 `onCredentialsCleared(handler)`，store 订阅它把 `user` 置空、
  `restored` 置 true（服务端已经明确否认，这是确定答案）。
  没有它就会出现"token 没了、顶栏还显示昵称头像、页面每个请求都 401"。

### 顺带修掉的三个小缺陷

- **后台 404 掉回前台布局**：`/admin/typo` 落到顶层兜底路由（没有 `layout`），
  侧边栏消失、用户以为自己被登出。给 `/admin` 加了内部兜底路由。
- **登录成功提示"欢迎回来，访客"**：`success` 文案是**调用前**求值的，
  而 `auth.displayName` 要等登录成功才有值。`useAction` 的 `success`
  现在支持传函数，在成功那一刻求值。
- **上传没有进度、且共用 20s 超时**：`attachmentApi.upload` 早就支持
  `onProgress`，但没有任何调用方传过；5MB 封面图在 2Mbps 上行需要约 20 秒，
  必然超时。现在 `useUpload` 暴露 `progress`、媒体库显示进度条，
  上传单独用 120s 超时。

|---|---|

### 踩坑备忘

- **改语义就必须改用例，而且要区分"用例错了"和"代码错了"**。
  `http.spec.ts` 里两条用例断言"401 → `location.replace` 被调用一次"——
  它们锁的正是旧行为。新语义下"公开页面不跳转"，所以用例要改成
  **两个场景各一条**（公开页不跳、后台页才跳），而不是把断言删掉。
  同时那两条用例暴露了我第一版的真 bug：新分支漏了 `tokenStore.access` 判断，
  把"完全匿名的 401"也说成了"登录已过期"——既有的
  「401 且无 detail 时使用兜底文案」用例当场抓住。

  "无法访问此网站"。跑脚本前先 `curl` 一下两个端口，比事后排查省事。

## 批次 5 · 生产库终于有备份路径了（以及文档基线收敛）

### 起因：备份能力装在了用不到的那个方言上

`backend/scripts/backup_db.py` 的文档字符串写得很讲究：解释了为什么必须用
`VACUUM INTO` 而不是复制文件（WAL 下直接 `cp` 会拿到不一致快照）。
但脚本对非 SQLite 的处理是**直接拒绝**，只留一句"PostgreSQL 请用 pg_dump"。

而 `docker-compose.yml` 里生产库就是 `postgres:16`。于是实际状况是：

- 生产部署（compose）的两个数据卷 `pgdata` / `mediadata` **没有任何备份路径**；
- 精心打磨的那条备份路径，只服务于开发用的 SQLite。

同类问题在 `deploy/nginx.conf` 上也成立：它只有 `listen 80`，没有 TLS ——
而 README 的部署章节读起来像是"可以上线了"。

### 改了什么

**1. 备份脚本支持两种方言**（`backend/scripts/backup_db.py`）：

| 方言 | 做法 | 恢复 |
|---|---|---|
| SQLite | `VACUUM INTO`（不变） | 放回文件（记得删 `-wal` / `-shm`） |
| PostgreSQL | `pg_dump -Fc`；宿主没有 `pg_dump` 时自动 `docker exec <容器> pg_dump` | `pg_restore --clean --if-exists` |

要点：

- 两条路径都产出 **custom 格式**（`-Fc`）：支持并行恢复、按表恢复、自带校验；
- 密码走 `PGPASSWORD` 环境变量而不是命令行（否则会出现在进程列表里），
  错误提示里的连接串用 `dsn` 属性**去掉密码**；
- URL 里的百分号编码要解码（`p%40ss%20word` → `p@ss word`）；
  docker 路径刻意不传 `-h/-p`（容器内连自己的 5432，宿主端口反而连不上）；
- 轮转同时认 `.db` 与 `.dump` 两种后缀 —— 只认一种，另一种会无限堆积
  （"从 SQLite 切到 PG"之后必然发生）；
- 备份失败时**删掉半成品文件**：宁可什么都没有，也不要一个不完整的 dump。

**2. 备份必须被验证过**。这一条是整批工作里最关键的：

```
pg_dump（docker exec 路径）→ 产出 0.04MB .dump

pg_restore --no-owner -d blog_restore_test

表数量 13（11 张业务表 + alembic_version + article_tags 关联表）✅
trgm 索引 3 条 ✅    alembic_version = a7c1e9d4b2f8（head）✅

**没有这一步的备份等于没有备份**——文件存在、大小正常、恢复时才发现是空的，

## 批次 6 · fail-closed 三件套（含一个被注释掩盖的中间件顺序缺陷）

> 触发点：另一份独立评估（`docs/ASSESSMENT-2026-09-22.md`）点了三条 P2，
> 复核后**全部成立**。三条都属于同一类——"防护写了，但判据本身可以被绕过/被误解"。

### 1. `APP_ENV` 写错 → 整个生产门禁静默失效

`is_production` 的实现是 `app_env.lower() == "production"`，而整个门禁
（默认密钥 / 默认口令 / DEBUG / DB_AUTO_CREATE / SEED_DEMO_DATA）都挂在它上面。
于是 `APP_ENV=prod`、`APP_ENV=prd`、`APP_ENV="production "`（末尾空格）
都会让门禁**整体不生效**，而服务照常启动、日志里一句警告都没有。

改法：`APP_ENV` 变成白名单（`development` / `testing` / `production`）+
归一化（去空白、转小写），未知值**直接拒绝启动**。这条同时改了契约：
原先 `APP_ENV=local` 是合法的，现在会拒绝——既有的
`test_non_production_is_never_blocked` 里那个 `local` 因此被移除，
并在用例注释里写明原因。

### 2. 公开读接口没有任何缓存头

前台只读接口（文章列表/详情/归档/搜索、分类、标签、系列、站点、评论列表）
既没有 `ETag` 也没有 `Cache-Control`，只有 RSS/sitemap 有。
新增中间件 `api/cache.py`：

- ETag 由**响应体**算（sha256 前 32 位，弱验证器）。不用
  `max(updated_at)` 这类版本号，是因为那要求每个查询都把版本信息带出来，
  漏掉任何一张相关表就会产出**过期 ETag** —— 客户端拿着 304 一直看旧内容，
  属于最难查的一类 bug；
- 只对**匿名 GET** 生效，排除 `/manage`、`/revisions` 与非 200；
- `max-age=60`：定时发布的文章到点才可见，缓存太久会让"我设了 10:00 发布，
  10:01 还没出现"变成投诉。

### 3. `is_production` 之外，还发现一个**被注释掩盖**的真缺陷

写缓存中间件时要决定注册顺序，于是去核对既有代码。原注释写着：

> 请求 ID 与访问日志。放在 CORS 之前注册：中间件是「后注册先执行」，
> 这样即使请求被 CORS 拒绝，也能在日志里留下带 request_id 的记录。

**注释与代码效果恰好相反。** 实测：发一个来自非白名单 Origin 的预检请求，
返回的 400 响应里**没有** X-Request-ID —— 说明 CORS 在外面截住了请求，
`RequestContextMiddleware` 根本没跑到。也就是说"被 CORS 拒掉的请求"
在日志里完全消失，而这正是注释想避免的事。

正确规则是「**后注册的在外层**」，于是按内→外重排为：

```
RequestContext（最外：所有请求都留痕，包括被 CORS 拒的）
  └── PublicCache（200 折叠成 304，日志里记的才是真实状态码）
        └── CORS
              └── 路由
```

这条顺序还有第二个好处：日志里记录的是**折叠后**的 304。
反过来（RequestContext 在内）每个 304 都会被记成 200，
"缓存到底省了多少"就永远算不出来。

### 4. HSTS：必须条件式，否则纯 HTTP 部署会把自己锁死

`deploy/nginx.conf` 只监听 80（TLS 由外层终止）。无条件发
`Strict-Transport-Security` 会把"本站只能用 HTTPS"写进访客浏览器
max-age 那么久，而服务端**撤不掉**这个记忆。改成按 `X-Forwarded-Proto` 判断：

```nginx
map $http_x_forwarded_proto $hsts_header {
    default "";
    https   "max-age=31536000; includeSubDomains";
}
```

（nginx 对空值的 `add_header` 不会发出该头，正是这里要的语义。）

**验证方式**：本机 Docker 守护进程没在运行，`nginx -t` 跑不了。
改用 nginx 配置解析器 `crossplane` 做语法与**指令上下文**校验：
直接解析这个文件会报 `"map" directive is not allowed here` ——
这是**独立解析的误报**（该文件是被 include 进 `http{}` 的，
同文件里的 `upstream` 也是 http 级指令且一直在正常工作）。
于是把内容包进 `events{} http{ ... }` 再解析：**status: ok**，
并确认 AST 里 `map` 的两个分支与 `add_header ... $hsts_header always` 都在。
这条"为什么要包一层"的理解也写进了测试注释，避免后人误改。

| `pytest tests/test_production_gate.py` | **20 passed**（原 10 条，改了 1 条契约、新增 8 条白名单用例） |

- **注释也可能是错的，而且错得更危险**：代码读起来像"已经考虑过 CORS 了"，
  只有实测（发一个被拒的预检，看响应头）才暴露它从来没生效过。

  半年后有人看到 git 历史会以为是为了让测试通过。

## 批次 7 · views 层测试：补上最大的覆盖空洞，顺带捞出两个真 bug

覆盖空洞是审计里排第一的前端问题：**22 个 view / 4049 行、零个 spec**，
其中 `ArticleEditView` 619 行是最大的风险点——改 UI 只有 34 项浏览器冒烟兜着，
而冒烟能抓"白屏"，抓不到"状态流转错了"。

这一批由一个子代理并行完成（我在同一时间做批次 6），纪律是：

## 批次 8 · HEAD 全线 405，以及我自己埋进去的一个缓存 bug

### 1. HEAD 请求全线 405（既有缺陷）

验证缓存改动时顺手 `curl -I` 了一下，拿到 `405 Method Not Allowed`。
排查下来是**故意的**差异：Starlette 的 `Route` 会给 GET 自动补 HEAD
（`starlette/routing.py:238` 的 `if "GET" in methods: methods.add("HEAD")`），
而 FastAPI 的 `APIRoute` 没跟这条 —— 于是本项目所有 GET 端点都不支持 HEAD。

为什么值得修：HEAD 是**缓存/CDN 内容再验证**（先问"变了吗"、不传正文）、
监控探活、以及排查时最顺手的 `curl -I` 的通用手段。一个"支持 GET 但不支持 HEAD"
的 API 在中间层看来是残缺的。

实现用纯 ASGI 中间件（`HeadMethodMiddleware`），三个要点都是踩过才知道的：

1. **只改内层 scope 的方法名**：外层（访问日志、限流、CORS）看到的仍是 HEAD，
   否则日志会把 HEAD 记成 GET，观测数据静默失真；
2. **正文丢掉、头部保留**，包括 `Content-Length` —— HEAD 的语义就是
   "头部与 GET 完全一致，只是没有正文"，所以实测对比了两者的 content-length
   （4686 = 4686）；
3. **必须在 PublicCache 外层**：ETag 是对响应体取哈希算出来的，
   如果正文先被清空，所有资源的 ETag 会退化成"空串的哈希"（同一个值），
   缓存语义直接失效。位置写错不会报错，只会让缓存悄悄失效 —— 所以顺序
   在代码注释与测试里都钉了一遍。

### 2. 我上一批加的缓存，把"读己之写"打穿了

**这是自己引入的 bug，而且是浏览器端到端脚本抓到的，单测完全看不见。**

现象：`full-check` 的 `A5b 修改分类` 失败，而且**失败详情是空的**
（`record(name, ok)` 只传了布尔）。为了定位，先把这条用例改成"失败会自证"：
找不到行 / 找不到编辑按钮 / 编辑器没打开分别返回不同 reason，
并带上当时的列表文案与条目。改完立刻拿到现场：

```
❌ A5b 修改分类 — 没找到包含该分类且带按钮的容器
   | 列表=全部分类 3 技术笔记/tech… 生活随笔/life… 读书观影/review…
```

新建的分类（API 确认存在，id=4）**不在页面上**：列表只有 3 个。

根因是我在批次 6 加的 `Cache-Control: public, max-age=60`：同一个 URL
既服务匿名公开页、也服务已登录后台（`/categories`、`/tags`、`/site/profile`
都是这样），而浏览器缓存**只按 URL 匹配**。于是：

1. 运行开始时匿名访问首页 → `/api/v1/categories?with_counts=true` 被缓存 60 秒；
2. 登录后进入分类管理、新建一个分类、重新拉同一个 URL →
   **命中那份匿名缓存** → 新分类不在列表里。

修法是给被缓存的响应加 **`Vary: Authorization`**（与 CORS 的 `Vary: Origin`
合并、不覆盖）。这样匿名那份缓存不再匹配带凭证的请求，后台永远是新鲜数据；
匿名访客之间照样共享缓存 —— **收益保留，正确性回来**。

为什么单测抓不到：视图单测里 `@/api` 的方法被 spy 掉了，压根没有 HTTP 层，
更没有浏览器缓存。这是"必须在真实浏览器里跑一遍"的又一个具体理由。

### 怎么验证的

| 验证项 | 结果 |
|---|---|
| 真 HTTP：`curl -I /api/v1/articles` | 200 + ETag + Cache-Control + content-length 4686（与 GET 一致） |
| 真 HTTP：`If-None-Match` | 304 |
| 真 HTTP：带 Authorization | 缓存头 0 个 |
| 真 HTTP：访问日志 | `"method": "HEAD"` |
| `curl -I /api/v1/categories` | `vary: Authorization` |
| 浏览器：smoke / interaction / full-check | **34/34、22/22、41/41**（修复前 A5b 稳定失败，修复后通过） |
| e2e_live | **62/62** |
| 后端全量 | **528 passed, 5 skipped**，覆盖率 82.73% |

### 踩坑备忘

- **一条只会说"失败"的断言，会让人多花一整轮去定位**。`record(name, ok)`
  改成"失败时带上现场"之后，一次运行就把范围缩到了"DOM 里没有这个分类"。
  写端到端脚本时，"失败详情"的重要性和断言本身一样高。
- **缓存的作用域是 URL，不是"这个接口是不是公开的"**。我原来的判断是
  "公开读接口可以缓存"，漏掉的是"同一个公开接口也被后台复用"。
  凡是给共享缓存加 `public`，都要同时问一句：**同一个 URL 会不会被
  带身份的场景读？** 会，就必须 `Vary`（或者干脆分开端点）。
- 我修完 HEAD 之后，第一次把 `HeadMethodMiddleware` 注册在了**最内层**，
  与自己在同一个提交里写下的注释（"必须在 PublicCache 外层"）相反。
  是"ETag 会不会对所有资源都一样"这个具体的检验点让我发现了它 ——
  **给顺序类改动配一个可观测的判别点**，比反复读代码有效。

## 批次 10 · 刷新令牌轮换：把无状态凭证变成可吊销的会话

### 问题（最初审计里列的第 4 条，一直留到现在）

refresh token 在此之前是**完全无状态**的：`security.py` 认真地生成了 `jti`，
注释写着"便于将来做黑名单/单点登出"—— 但从来没有任何地方存过它。
于是"吊销"只剩一条路：`users.token_version += 1`，那是**全端下线**。
两个后果：

1. **泄露后无法止损**：被偷走的 refresh token 在 7 天有效期内可以反复换出新的
   access token，服务端既看不见、也拦不住；
2. **泄露面单调增长**：每次 `refresh()` 都签发新令牌，而旧令牌**继续有效**——
   每刷新一次就多一枚可用凭证。

### 方案

新增 `refresh_sessions` 表（一行 = 一枚已签发的 refresh token）：

| 列 | 用途 |
|---|---|
| `jti_hash` | jti 的 SHA-256（**只存哈希**：库被拖走也伪造不出令牌） |
| `expires_at` | 过期时间（与 JWT 的 `exp` 一致） |
| `rotated_at` / `replaced_by` | 轮换时间与"换成了哪一枚"（排障能顺着链看） |
| `revoked_at` | 按行吊销（登出 / 改密码 / 检测到复用） |

三条契约：

- **轮换**：刷新时签发新令牌并把旧的标记为已轮换；
- **复用检测**：已轮换的令牌再次出现 ⇒ 判定盗用 ⇒ **吊销整族**（OAuth 2.0 的
  标准做法：宁可让用户重新登录，也不假设拿旧令牌的人是谁）；
- **按会话吊销**：登出与改密码现在会真的把这些行标记为已吊销，
  不再只依赖"代次 +1"（代次仍保留 —— access token 是无状态的，只有它能立刻作废）。

### 那个必须做的折中：30 秒宽容窗口

严格轮换会误伤一个日常场景：**两个标签页的 access token 同时过期**。
前端的单飞锁（`refreshPromise`）只在单个页面内生效，跨标签页无效；
localStorage 虽然共享，但两个标签页可能几乎同时读到同一个旧 refresh token。
若不加处理，第二个标签页会触发"复用检测"，把用户**从所有设备踢下线** ——
一个内部竞态被当成盗用来处理，比不检测还糟。

所以：`rotated_at` 在 30 秒内的重放按"再来一次"放行，超出窗口才判定复用。
取 30 秒的依据是"跨标签页的两次刷新通常相差毫秒级到一两秒"，
而盗用者往往有更长的间隔。

**写测试时我在这里犯过一个错**：第一版用例断言"轮换后旧令牌立刻 401"，
结果失败了 —— 因为它在窗口内重放，而窗口内本就该放行。
用例报错暴露的是**我的用例与契约不符**（也顺带暴露我文档里"旧的立刻作废"
这句话不准确）。现在拆成三条：轮换会签发新令牌并记录两行、
窗口内重放被容忍、窗口外重放被拒并吊销整族。

### 跨方言的坑：SQLite 的时间是 naive

第一次跑测试就炸：

```
TypeError: can't compare offset-naive and offset-aware datetimes
```

SQLite 把时间存成字符串，取出来是 **naive**；PG 的 `timestamptz` 取出来是 aware。
`record.expires_at <= datetime.now(UTC)` 于是只在 PG 上成立。

修法不是就地补 tzinfo，而是**用仓库里早就为此准备好的类型**：
`db/types.py::UTCDateTime`（`process_result_value` 里统一补 UTC）。
它的 docstring 写的就是这个场景 —— 说明这个坑项目以前踩过并沉淀了方案，
我第一版没去找它，白踩了一次。

### 升级须知（诚实披露）

**升级后所有现存 refresh token 会失效，需要重新登录一次**：它们在库里没有
对应记录。access token 不受影响（不查这张表），会在 120 分钟内自然过期。
个人博客是单用户自用，这个代价可以接受；如果这是多用户系统，
需要一个"识别为旧令牌则放行一次并补登记"的过渡逻辑 —— 这条写进了迁移的
docstring 与 CHANGELOG。

## 今日学习清单

- GitHub Actions 的 `ubuntu-latest` 镜像自带 `/usr/bin/google-chrome`，
  所以"跨平台探测"不需要额外的安装步骤，只需要不写死路径。
- `--disable-dev-shm-usage`：容器与 CI runner 的 `/dev/shm` 常常只有 64MB，
  不加会随机崩在渲染上——表现是"用例莫名其妙挂了一条"，很难归因。
- `pytest-cov` 的 `fail_under` 只在带 `--cov` 时生效；写在配置里但 CI 不带
  `--cov`，等于门槛不存在（这正是本仓库此前 82% 覆盖率却没门槛的原因）。
- **asyncpg 的连接绑定事件循环，aiosqlite 不绑定**——所以"只在 SQLite 上跑过"
  的测试套件，永远发现不了跨 loop 复用连接池的问题。
- **SQLite 不校验 `VARCHAR(n)` 长度，PostgreSQL 校验**：同一份测试数据在
  两种库上的行为可以完全不同，而失败信息（`StringDataRightTruncationError`）
  指向的是"产品有问题"的错觉，实际是测试数据造错了。
- PG 13 起 `pg_trgm` 是 **trusted extension**，库 owner 就能 `CREATE EXTENSION`，
  不需要超级用户——这让"迁移里建扩展"在托管环境里也可行。
- 三元组索引救不了 1–2 字的 LIKE 查询：`%数据%` 里连一个完整三元组都提不出来。
  这与 FTS5 选 `trigram` 分词器后的限制是同一件事，两个方言在这点上**恰好一致**。
- **DOMPurify 的 `forceKeepAttr` 会跳过"把裁剪后的值写回 DOM"这一步**——
  它表达的是"这个属性原样保留"，不是"我改过的值保留"。想在钩子里改值，
  属性本身必须仍在白名单里。
- `new URL(href, origin)` 能识别协议相对地址（`//evil.com`），
  `/^https?:\/\//` 不能 —— 而浏览器对前者是照常解析并跳转的。
- **注释会撒谎，而且比没注释更危险**：`main.py` 里"放在 CORS 之前注册…
  即使被 CORS 拒绝也能留下记录"读起来像已经处理过了，实测才发现恰好相反。
  顺序、优先级、默认值这类不可见行为，只能靠"一个会失败的观测"来确认。
- nginx 的 `map` / `upstream` 是 **http 级**指令：文件放在 `conf.d/` 里没问题，
  一旦被挪成主体配置（带 `events{}` 的那层）就会启动失败。
  用 `crossplane` 校验时要**把内容包进 `http{}` 再解析**，否则会得到
  `"map" directive is not allowed here` 这种误报。
- `add_header` 在值为空字符串时**不会**发出该头 —— 这正是条件式 HSTS 的实现依据。
- **给共享缓存加 `public` 之前，先问"同一个 URL 会不会被带身份的场景读"**：
  浏览器缓存只按 URL 匹配，而同一个公开接口常常也被后台复用
  （本项目的 `/categories`、`/tags`、`/site/profile`）。答案是"会"就必须
  `Vary: Authorization`，否则后台会出现"新建成功但列表里没有"这种读己之写失效。
- **一条只会说"失败"的断言，会让人多花一整轮定位**：端到端脚本里
  `record(name, ok)` 改成"失败时带上现场（列表文案、条目、哪一步没找到）"之后，
  一次运行就把范围缩到了具体环节。
- **顺序类改动要配一个可观测的判别点**。中间件注册顺序（谁在外层）写错不会报错，
  只会静默改变行为：判断 HEAD 中间件位置对不对的判别点是
  "ETag 是不是对所有资源都一样" —— 有这个点，才不用反复读代码猜。
- FastAPI 的 `APIRoute` **不会**像 Starlette 的 `Route` 那样给 GET 自动补 HEAD。
  想要 HEAD 必须自己加（或写中间件）。
- **SQLite 存的时间取出来是 naive，PG 的是 aware**：跨方言比较时间必须用
  `db/types.py::UTCDateTime`。这个坑项目以前踩过并沉淀了类型装饰器，
  我第一版没用它，白踩了一次（`can't compare offset-naive and offset-aware`）。
- **"轮换"这类安全机制要给它留一个竞态窗口**：多标签页同时刷新是**正常行为**，
  严格实现会把内部竞态当成盗用来处理（把用户从所有设备踢下线）。
  窗口大小要有依据（这里是"跨标签页刷新通常相差毫秒级"），并且要写进文档与用例。
- 写测试时如果用例失败，先分清是**代码错**还是**用例与契约不符**：
  这次是后者（我断言"旧令牌立刻失效"，而契约允许 30 秒内重放），
  顺着它还发现文档里"旧的立刻作废"这句话本身就不准确。
