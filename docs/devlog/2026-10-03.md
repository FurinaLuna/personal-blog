### 事情本身

有人（另一个 AI）看了一份失败日志，给出了这样的分析：**「点回顶后 `scrollY=26`，
说明前端 smooth 滚动没走完就断言了，建议把回顶改成瞬移」**。它给的机制解释是对的
（平滑滚动 + 不等动画结束就断言 = 读到中间值），但它引用的那条**断言文本**在仓库里
从未存在过：

```
历史日志：PATCH 返回 200 且 fields=[]        ← 仓库里没有这个字符串（现在的断言写「字段=」）
          点击回顶后 scrollY = 26            ← 旧版断言的产物：点完立刻读
```

`git log -S` 全历史搜索 `fields=`、`jumpScroll`、`e5BackTo`、`60 waitFor scrollY`：
**只有 `c3afccf` 一次提交**——E5 这条断言是那天连同「目录改造」一起从零写下的，
写的时候就已经是「点击后轮询、再读落点」的形式（注释原文：*「点一下要真的回顶：
组件用的是 smooth 滚动，轮询等它走完再读」*）。也就是说，**26 是旧版测试工具的
产物，而不是当前代码的行为**；这份分析把「一条已经不存在的断言的输出」当成了
「现在的缺陷」。

> 这也是为什么这条日志值得留档：**外部分析的结论对不对，取决于它看的是哪一版**。
> 分析报告的语气通常比它的版本意识更自信。

### 那 13 是什么

留在两份报告里的实测数字是 **13**，两次独立日期（09-30 / 10-03）完全一致：

```
E5 … 点击回顶后 scrollY=13
```

一致而不是抖动，说明它不是随机时序，而是**浏览器平滑滚动的落点偏差**：组件走
`window.scrollTo({ top: 0, behavior: 'smooth' })`，Chromium 最终停的位置离顶部还差
十几像素。这条判据当时的阈值是 `< 20`，所以一直是绿的——但**绿得没有余量意识**：
再漂一点就要误报，而报告里根本看不出「13 已经贴线」。

所以本批不改产品行为（瞬移回顶会让读者丢失位置感，那是计划 §3.3 明确否决过的方案），
只把**测试的读法**改对：

- **读法**：点击后在页面内按 100ms 采样，**连续两次相同**才算停稳（上限 80 次）。
  原来的 `waitFor(window.scrollY < 60)` 会在动画途经 59 时就成立并读回中间值——
  那正是外部日志里 26 的来源形态。停稳判据同时也挡住了「动画被中断停在半路」
  （那种情况会一直停在同一个值上，随后被落点断言判红）。
- **阈值**：保留 `< 20`，**没有**收成 `< 10`。理由是它在两页两距离上不是同一口径
  （smoke-check 那条 `<10` 是在 600px 处点击的另一页），而我无法在本机复现验证
  （见下）——**不把自己没验过的数字写进断言**。落点数字一律进 detail。

### CI 那一处放宽

`.github/workflows/ci.yml` 的「等待服务就绪」从 `seq 1 60` 改成 `seq 1 120`。
这条在 CI 上**从未真的触发过**（每次失败的注解都指向具体断言，不是这里），
所以它是纯余量调整：代价是失败时多等 60 秒，换来的是不必用「重跑一次」去区分
「runner 慢」与「代码坏」——后者才是这条步骤该保留的信号。

### 教训

1. **外部分析要先核对「它看的是哪一版」**。引用的输出字符串能否在 git 历史里找到，
   是最省事的一次核对——搜不到就说明分析对象不对，后面所有结论都不必再看。
2. **判据绿色不等于判据有余量**。13 对 20 是绿的，但外部一看到 26 就会写成缺陷。
   把实测值放进 detail（而不是只放「通过」），失败时能直接看到数字，也不必翻截图。
3. **不把没验过的数字写进断言**。本批有能力把阈值收成 10（smoke 那边就是 10），
   但在无法本机复现的前提下收了它，等于给自己埋一条只能靠 CI 试出来的红灯。
