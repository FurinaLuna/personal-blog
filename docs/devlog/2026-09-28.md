# 2026-09-28

## 批次 1：前台「登录」入口做成后台开关（`site_profile.show_login_entry`）

### 需求与判断

需求原话：**登录按钮能不能在后台设置开关决定要不要显示在前端。**

能，而且它不该被做成一件事新机制 —— `site_profile` 这张单行表里已经有
`comment_need_approval` / `allow_guest_comment` 两个同类策略开关，后台设置页有现成的
「评论策略」勾选框区，前台顶栏读的又是同一份 `/api/v1/site/profile`（由 `DefaultLayout`
在挂载时灌进 Pinia）。所以本轮只加了「一列 + 一个勾选框 + 一处渲染判断」，
没有引入任何新的配置通道或状态源。

### 关键设计：入口开关 ≠ 权限开关

这是本轮唯一需要想清楚的地方，也是**必须写进文档**的一条：

| 关掉开关之后 | 行为 |
|---|---|
| 前台顶栏的「登录」链接（桌面 + 移动端抽屉） | **不渲染** |
| `GET /login` 登录页路由 | **照旧可访问** |
| `POST /api/v1/auth/login` | **照旧可用** |
| 已登录时顶栏的「后台 / 进入后台」入口 | **照旧显示**，不受开关影响 |

为什么不做成"前台彻底登不进来"：隐藏入口的目的是**让访客看不见**，
而站长自己还得进得去 —— 那只能靠**直接访问 `/login`**。如果顺手把路由或接口也关掉，
站长就被自己的开关锁在门外了。所以这条分界线由一条后端用例钉住
（`test_login_entry_switch_does_not_disable_login`：关掉开关后仍然登录得成功），
谁哪天把开关接到登录链路上，它立刻变红。

后台勾选框的说明文字也写明了这一点（"这只是入口开关，不是禁用登录"），
免得站长了几个月后自己也忘了入口藏哪儿。

### 迁移：`server_default=TRUE` 是必要的，而且不能事后 drop

生产库的 `site_profile` **已经有那一行数据**。`ADD COLUMN ... NOT NULL` 在已有行上
必须能拿到值，否则迁移直接失败 —— 所以默认值由数据库侧给。

取 `TRUE` 的用意是**升级不改变任何可见行为**：升完前台照旧显示登录入口，想关再去后台关。

探针实测（`.migr-probe/probe.py`，先升到旧版本、插一行存量数据，再升到 head）：

```
存量行已插入（此时没有 show_login_entry 列）
存量行的 show_login_entry = 1（期望 1/True）
列定义含 DEFAULT：True
=== downgrade -1 ===  → 列还在吗：False
=== 再 upgrade head === → 存量行的 show_login_entry = 1
alembic heads → 4fca195eccc9（单头）
```

### 测试与反向验证

前端新用例覆盖四个契约：默认显示、**两个渲染位**都受开关控制、已登录的「后台」不受影响、
档案加载失败时仍显示（降级方向与默认行为一致）。

两条**反向验证**（把修复改坏，确认用例真的会红）：

```
1) store 里把开关短接成恒真（= 改造前的行为）
   → × 后台关掉开关后，桌面与移动端两处都不再渲染登录入口
2) 把「后台」入口也挂到同一个开关上（= 站长被锁在门外的写法）
   → × 已登录时「后台」入口不受开关影响
```

两条各自只让**对应的那一条**变红，说明判据是分开的，没有互相掩护。

后端侧的新用例同样有判别力：`test_login_entry_switch_does_not_disable_login`
在"把开关接到登录接口"的假设下必然失败。

### 真机验证：E4 第一版是**假失败**，值得记一笔

`full-check.mjs` 新增 E4：API 切开关 → 重新加载首页 → 数顶栏里的登录入口。

第一版结果：

```
❌ E4 … — 关：HTTP 200 字段=false 渲染 0 个；开：HTTP 200 字段=true 渲染 0 个
```

两个状态都是 0。原因不是功能坏了，而是**浏览器当时是已登录状态** ——
E4 前面的 B4 用例（"非站长访问后台被弹回首页"）会把浏览器登成临时 author，
而已登录时顶栏渲染的是「后台」，任何开关状态下都不会有「登录」入口。
补一句 `Network.clearBrowserCookies` 切回匿名后：

```
✅ E4 … — 关：HTTP 200 字段=false 渲染 0 个；开：HTTP 200 字段=true 渲染 1 个（初始 true）
```

这里有个值得保留的性质：**"恢复后有 1 个"这条断言让"浏览器已登录"这种前提错误
表现为失败，而不是假绿**。如果当初只断言"关掉后是 0 个"，这条用例会永远绿着、
且什么都没验证。

另一处环境坑：`/api/v1/site/profile` 是公开可缓存接口（`max-age=60`）。
不断言前先 `Network.setCacheDisabled(true)`，否则第二次加载会命中浏览器缓存里的旧档案，
表现为"开关关了前台还显示"——又是一条假失败。

### 一处测试脚手架的坑

`SettingsView.spec.ts` 里既有的 `fieldControl(wrapper, label)` 取的是 label 内**第一个**
`span` 的文本，而开关类字段的 label 是「标题 span + 说明 span」两层结构，
第一个 span 的 `text()` 会把说明一起拼进来，永远比不中。
新增了 `switchByLabel()`（"某个 span 的文本恰好等于标签"）并在注释里写清了原因，
没有去改 `fieldControl` —— 它被十几个既有用例依赖，改动它的语义风险大于收益。

### 已知限制与可选后续

- **开关生效有延迟**：公开档案带 `max-age=60`，且前台 store 在 SPA 会话内只加载一次。
  已经打开的访客页面要等一次整页刷新（且缓存过期）才会变化。对"站长偶尔调一次"的
  场景足够，若要做到即时生效，得给档案加版本号 + 前端轮询，代价不成比例。
- **想连入口路径一起藏**（例如登录页改到只有自己知道的地址）是另一件事：
  那会动到路由与 `SITE_*` 配置，且必须保证站长永远进得去，本轮刻意没做。
- README / ROADMAP 里的测试数量仍然是硬编码，每批都在漂（本轮又改了一次）。
  要根治得让 CI 用 `pytest --collect-only` 与 vitest 的实际计数去比对文档，
  属于独立的一块工作。
