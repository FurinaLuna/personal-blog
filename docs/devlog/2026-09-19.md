## 批次 1 · 部署加固与依赖锁定

A1 与 A2 改的是同一处（`deploy/Dockerfile.backend` 的 `CMD` 行与 compose 的
backend 服务），拆成两次提交会留下「文件改了一半」的中间状态，所以合并为一次
「部署加固」提交，日志里分开记述。

### A1 统一 XFF 信任策略

- **文件**：`deploy/Dockerfile.backend`、`docker-compose.yml`
- **根因**：项目里有**两个独立的 XFF 信任开关**，且默认配置互相矛盾 ——
  uvicorn 的 `--proxy-headers --forwarded-allow-ips *` 会在应用之前按
  `X-Forwarded-For` 改写 `scope["client"]`，于是应用层
  `TRUST_PROXY_HEADERS=false` 这道防线被完全架空：
  `client_ip()` 回落到 `request.client.host`，而那个值已经是客户端可控的。
- **实测确认**（本次会话，对本地后端）：

  | 启动方式 | 5 次不同伪造 XFF 后的 ΔUV |
  |---|---|
  | 默认（`--proxy-headers` 开，信任 127.0.0.1） | **5** —— 每个伪造值都是一个"新访客" |
  | `--no-proxy-headers` | **1** —— XFF 被忽略 |

  开发态就复现了，因为本机即 `127.0.0.1`，落在 uvicorn 的默认信任范围内。
  生产态更糟：`--forwarded-allow-ips *` 信任所有 peer，而 compose 又把
  `8000` 发布到宿主机，任何能直连后端的人都能伪造 IP，绕过全部限流。
- **修法**：把信任判定**收敛到应用层一处**。
  1. `Dockerfile.backend` 的 `CMD` 改为 `--no-proxy-headers`，uvicorn 不再插手；
  2. `docker-compose.yml` 给 backend 显式设 `TRUST_PROXY_HEADERS: "true"`
     （它确实在 nginx 之后，不开的话全网共用一个限流桶、UV 恒为 1）；
  3. **删掉 `ports: ["8000:8000"]`**，改为 `expose`。后端只应经 nginx 从
     compose 内网访问 —— 一旦映射到宿主机，nginx 那层的限流、CSP、
     安全响应头就全部失效。
- **验证**：`docker compose config` 静态校验通过，确认 `TRUST_PROXY_HEADERS: "true"`
  已注入、`ports` 已消失、只剩 `expose: ["8000"]`。

### A2 `--workers 2` 的两个后果

- **文件**：`deploy/Dockerfile.backend`、`backend/src/app/services/seed.py`
- **后果一：限流配额翻倍**。限流器是进程内的（`utils/ratelimit.py` 自己也
  写明了这个边界），而 `--workers 2` 让实际放行量乘以 2 —— 登录限流
  5/分 变 10/分。这不是理论风险，**镜像的默认配置就是它**。
- **后果二：冷启动竞态**。`seed_admin` 是 check-then-insert，两个 worker
  会双双通过 SELECT、双双 INSERT，后提交的撞 `users.username` 唯一约束；
  而 `lifespan` 里的异常会 **re-raise**，输掉的那个 worker 直接启动失败。

#### 修 seed 时踩的三个坑（都值得记）

**坑 1：教科书写法在本项目的主力数据库上不成立。**
第一版按 SQLAlchemy 的标准做法写了 `async with session.begin_nested(): await session.flush()`
再捕获 `IntegrityError`，想用 SAVEPOINT 把冲突隔离住。实测（SQLite 3.53 + aiosqlite）：

```
捕获到 IntegrityError: UNIQUE constraint failed: users.username
  对象是否还在 session 里: False
  是否可以继续查询：
  查询失败: PendingRollbackError
```

**SAVEPOINT 没有隔离这次失败** —— 整个 session 仍被置为「待回滚」，
后续任何查询都抛 `PendingRollbackError`。所以「捕获后回查一次就能救回来」
这个思路在这里根本走不通，不是代码写错，是前提不成立。

**坑 2：改用 upsert 后，`admin in session` 的 expunge 是多余的。**
在确认坑 1 之前我还试过「冲突后把对象摘掉再回查」，仍然失败 ——
因为 savepoint 回滚已经把对象摘掉了，而 autoflush 依然会重放那次插入。
这条弯路说明：**症状（PendingRollbackError）相同，根因可能完全不同**，
不在最小复现上确认就动手改，会连改两版都无效。

**坑 3：`from sqlalchemy import select` 的局部导入被顺手带出问题。**
改动过程中一次 `replace` 匹配到了错误的位置，留下了 35 行重复的残留
（旧的 `SiteProfile(...)` 参数块）。ruff 的 `invalid-syntax: Unexpected indentation`
直接指出来了 —— 大段替换后**立刻跑 lint** 是必要的，不能等到跑测试。

#### 最终修法

换成一条语句的原子 upsert：`INSERT ... ON CONFLICT DO NOTHING`。
SQLite ≥3.24 与 PostgreSQL ≥9.5 都支持，正好覆盖本项目支持的两个数据库。
把竞态从「查与插之间」压缩成一次原子写入，没有窗口可钻，
也就不需要异常处理路径 —— 顺带绕开了坑 1 和坑 2。

抽了 `_insert_ignoring_conflicts(dialect_name)` 做方言分发，
不支持的方言退回原来的 check-then-insert 并在注释里写明代价。

#### 「多 worker 现在安全了吗」——**没有，要分清**

修完 seed 后我用两个进程同时冷启动到同一个空库上实测：

```
:8032  HTTP 200       ← 正常启动
:8031  HTTP 000       ← 启动失败
  sqlite3.OperationalError: disk I/O error
users = 1             ← 没有重复，也没有唯一约束冲突
```

失败的进程拿到的是 **`disk I/O error` 而不是 `IntegrityError`** ——
说明 seed 的约束竞态确实修好了（没有重复 admin），但它死于另一个原因：
**两个进程并发对同一个 SQLite 文件做 DDL（`create_all`）本就不安全**。
这是 SQLite 的固有限制，不是 seed 的锅，也没有等价的 upsert 保护。

所以准确的说法是：**`--workers 1` 是当前架构下唯一正确的取值**，
要横向扩展得先换 PostgreSQL（解决并发 DDL）**并且**把限流换成共享存储
（解决配额翻倍）。这一条已写进 Dockerfile 的注释，避免下次有人"顺手调大 worker 数"。

- **验证**：
  - 单进程冷启动空库 → `users=1 profiles=1 articles=4`，`/health` 200
  - 重复启动 → 计数不变（幂等）
  - 两进程并发冷启动 → `users=1`，无唯一约束冲突
  - 新增 3 个用例（`tests/test_seed.py::TestSeedConcurrency`），
    用「只让第一次查重看不到已存在的行」精确模拟竞态窗口：
    断言走完「查不到 → 插入被忽略 → 回查」全过程，且**复用**而不是又插一条

### A3 Python 依赖锁定

- **文件**：`backend/pyproject.toml`、`backend/requirements.lock`（新增）、
  `.github/workflows/ci.yml`、`deploy/Dockerfile.backend`
- **根因**：全部依赖只有 `>=` 下界、无上界；唯一的锁文件 `uv.lock` 被
  `.gitignore:19` 排除。风险不是假设 —— **已经发生了**：

  | 包 | pyproject 写的 | 实际装出来的 |
  |---|---|---|
  | bcrypt | `>=4.2` | **5.0** |
  | aiosmtplib | `>=3.0` | **5.1** |
  | pillow | `>=11.3` | **12.3** |
  | pytest | `>=8.3` | **9.1** |

  都跨了一到两个主版本，只是恰好没坏。同一个提交在不同时间构建出的
  环境并不相同。

- **修法**（两步）：
  1. **加上界**：一律写成「下界 + 兼容上界」，允许当前已验证的主版本线、
     挡住下一个主版本。这是零维护的那一半，挡住的是"未知的未来主版本"。
  2. **生成完整锁**：在**全新的** venv 里装 `.[postgres,dev]`（用新 venv
     而不是复用开发环境，避免把调试包冻进去），再 `pip freeze`。
     锁里含 `asyncpg` —— 它只在生产镜像里用得上，而生产镜像正是靠这份锁构建的。
  3. CI 的 3 处安装步骤与 Dockerfile 都改成
     `pip install -r requirements.lock` + `pip install --no-deps -e .`
     （`--no-deps` 避免 pip 再解析一遍范围，与锁文件产生分歧）。

- **把「锁与范围必须一致」做成机器检查**：新增
  `tests/test_dependency_lock.py`（6 个用例）。漂移是必然会发生的 ——
  改了范围忘了重新生成锁，review 里几乎看不出来，症状却是
  「CI 装旧版本、本地装新版本，代码一个字没改」。用例覆盖：
  每个声明的依赖都在锁里、锁定版本满足声明范围、`asyncpg` 必须在
  （漏了它镜像构建直接失败，而那只有真跑 Docker 才会发现）。

  > 这个测试自己也抓到一个分类错误：第一版把 `build-system.requires`
  > （hatchling）也算作「必须进锁」，测试立刻报缺失。那是**测试的分类错了**
  > —— 构建后端由 pip 在隔离环境里临时安装，不进运行时环境。修的是测试。

- **验证**：`ruff` 全绿；`pytest` **379 passed**（新增 9 例）；
  `import-linter` 2 kept / 0 broken。

## 批次 2 附带发现并修复：一个已经推到 main 的严重回归

> **这一段是本日最值得读的部分。** 它说明：370 个后端用例 + 138 个前端用例 +
> smoke 34/34 + interaction 22/22 全绿，仍然可以漏掉「所有经编辑器发布的文章
> 对访客彻底不可见」。

### 现象

补跑 `full-check` 时 D8（二级评论）失败。第一版失败信息没说是哪一步失败，
补全后拿到 `已发表=false` —— 评论压根没出现。查后端日志：

```
POST /api/v1/comments/article/6 -> 404
```

文章 6 是 full-check 本轮新建并**已发布**的临时文章，评论却 404。

### 定位

404 来自 `comment_service` 的可见性检查。让 full-check 在后台跑、
**运行期间轮询数据库**，拿到文章 6 的真实状态：

```
id=6  status=published  published_at=None
```

**已发布，却没有发布时间。**

### 根因（是 2026-09-17 那批「定时发布」引入的）

`update()` 里我写的是：

```python
if "published_at" in data:            # ← 前端每次保存都会带这个字段
    requested = data.pop("published_at")   # None
    data["published_at"] = None            # ← 把 NULL 写回去
elif data.get("status") is PUBLISHED and article.published_at is None:
    data["published_at"] = datetime.now(UTC)   # ← 死代码，永远走不到
```

当时的**本意**是「显式传了时间就不能被『首次发布补当前时间』覆盖掉」，
所以用了 `elif`。但前端的 `buildPayload` 为了支持「清掉排期」，
**每次都显式传 `published_at: form.published_at || null`** ——
于是 `if` 永远命中，`elif` 成了死代码。

而「新建草稿 → 点发布」走的正是这条路径：草稿的 `form.published_at` 是空串
→ payload 里是 `null` → 发布后 `published_at` 仍是 `NULL`
→ `is_publicly_visible()` 返回 False → **对公众彻底消失**。

### 为什么这么难发现

三个"看不见"叠在一起：

1. **作者自己看得见**。`_can_view` 对作者放行，所以编辑器、后台列表、
   作者视角的详情页**一切正常**——写作者不会有任何察觉；
2. **列表页也可能看得见**（取决于查询路径），只有详情与评论是 404，
   现象零散；
3. **测试数据恰好绕开了它**。后端用例里创建文章时都是
   `status="published"` 且不传 `published_at` → 走的是**新建**路径
   （`_resolve_published_at` 正确补了 now）；而涉及改期的用例传的是
   **具体时间**，从没传过 `null`。也就是说：**测试发的请求和前端真正发的
   请求不是同一个形状**，这个缝隙正好是 bug 藏身之处。

`full-check` 是唯一走真实 UI 完整路径的，所以只有它抓到了。

### 修法

把不变量写清楚并直接编码：**published 状态不能没有发布时间**。

```python
status_after = data.get("status", article.status)
if data.get("published_at") is not None:
    data["published_at"] = _normalize_published_at(data["published_at"])  # 显式时间优先
else:
    data.pop("published_at", None)   # 没传或传 null：都不写 None
    if status_after is PUBLISHED and article.published_at is None:
        data["published_at"] = datetime.now(UTC)   # 缺了就补
```

关键差别：**不再用「字段在不在 payload 里」判断意图，而是用「值是不是 None」。**
前端总会带这个字段，所以「字段存在」不携带任何意图信息。

顺带抽出 `_normalize_published_at()`，让新建与更新共用同一套时区归一。

### 验证

```
修复前：草稿 -> PATCH {status:published, published_at:null}
        published_at=None   匿名详情 404   ← 对公众消失
修复后：published_at=<now>  匿名详情 200
对照：  已发布 -> PATCH {content_md, published_at:null}
        published_at 保持不变（重发一次不该让旧文掉出列表）
```

- `full-check` **41/41 通过**
- 新增 4 个用例（`TestPublishedAtInvariant`），其中一条直接断言
  「列表里出现的已发布文章都必须有时间」——即使将来实现再变，
  这条不变量也能兜住
- 存量数据核查：`published 且 published_at is null` 的文章 **0 篇**，
  用户真实数据未受影响（只有探针文章）

### 教训

1. **测试发的请求要和前端发的请求同一个形状。** 只要有一处不同（这里是
   「永远显式传 null」），那条缝隙就是 bug 的藏身处。E2E 走真实 UI，
   所以能盖住这类缝隙——这是它不可替代的价值。
2. **「用字段在不在来判断意图」是脆弱设计。** 前端为了支持「清空」总会带上
   字段，于是「在不在」不携带信息。判断依据应当是**值**。
3. **防御性的 `elif` 可能就是 bug 本身。** 我加它是为了「别覆盖显式时间」，
   结果它的前置条件（字段不存在）在实际调用下永假。
   写「保护性分支」时要问一句：**这个前置条件在真实调用下会成立吗？**
4. **作者可见 ≠ 公众可见。** 任何「只有作者能看到的失败」都必须在
   **匿名视角**下测一遍。这条以后要作为评审清单项。

## 今日学习清单

1. **同一件事有两层开关时，默认配置很可能互相矛盾。**
   `TRUST_PROXY_HEADERS=false` 看起来是安全的默认值，但只要 uvicorn 的
   `--proxy-headers` 开着，这个开关就永远读不到真实值。
   查安全开关时不能只看自己写的那一层。
2. **「实测」要选对观测口径。** 一开始我看的是 uvicorn 的 access log，
   它显示 `127.0.0.1` —— 但那不反映改写后的 scope。换成**访客 UV**
   才看到真相（ΔUV=5）。口径选错会得出"没问题"的相反结论。
3. **SAVEPOINT 在 SQLite/aiosqlite 上不隔离 flush 失败**（见坑 1）。
   教科书方案要先用最小复现验证前提，再动手改业务代码。
4. **症状相同不代表根因相同**（见坑 2）。`PendingRollbackError` 出现了两次，
   根因却是两个不同的东西。
5. **大段替换后立刻跑 lint**（见坑 3）。35 行重复残留是 ruff 先发现的，
   不是测试。
6. **修完一个连环故障要分清哪一段真的修好了。** 两进程并发冷启动仍然
   失败，但失败原因从 `IntegrityError` 变成了 `disk I/O error` ——
   这是"修好了甲、暴露了乙"，不是"没修好"。日志里必须写清楚，
   否则下一个人会以为修复无效。
7. **约定要变成测试才有约束力。** 「改了 pyproject 要重新生成锁」写在注释里
   等于没写；`test_dependency_lock.py` 才是那个会拦住你的东西。
8. **测试发的请求要和前端发的请求同一个形状**（见 D8）。只要有一处不同，
   那条缝隙就是 bug 的藏身处——后端用例永远传具体时间，前端永远传 null，
   于是「首次发布草稿」这条路径在所有单测里都是空的。
9. **「用字段在不在来判断意图」是脆弱设计**（见 D8）。调用方为了支持"清空"
   总会带上字段，此时「在不在」不携带任何信息，判断依据必须是**值**。
10. **写保护性分支时要问：这个前置条件在真实调用下会成立吗？**（见 D8）
    我加 `elif` 是为了"别覆盖显式时间"，而它的前置条件（字段不存在）永不成立，
    于是保护分支本身成了 bug。
11. **作者可见 ≠ 公众可见。** 任何"只有作者能看到的失败"都要在**匿名视角**
    下再测一遍。这条应当进评审清单。
